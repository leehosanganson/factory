# Define the REST MVP API and security contract

- **Type:** Approved design/implementation opportunity recorded during the self-improvement cycle; not a user-reported usability finding.
- **Context:** Factory has an immutable principal bearer verifier, but no HTTP server, OAuth integration, remote admission, or worker. The single-host REST MVP direction requires API schemas and authorization/reliability rules to be reviewable before credentials or remote work are accepted. The existing REST MVP design draft remains separate and must not be modified or copied into this change.
- **Desired outcome:** Add a concise, tracked contract for the MVP's first remote API routes and security behavior, grounded in the existing queue/principal verifier boundaries and explicit about which pieces remain unimplemented.
- **Scope:** Document `POST /work`, `GET /work/{id}`, and `GET /work/{id}/history`; OAuth initiation and callback security; caller-principal scoping; idempotent durable acceptance; bounded history and request limits; structured safe errors; relevant GitHub App permission minimum; security and non-goals. Remote submission supports a GitHub issue plus optional bounded supplementary instruction text. The issue remains the source reference; this is not arbitrary shell/command execution. No server, routes, OAuth, credential storage, remote admission, or worker code.
- **Decisions:** Use a request-scoped `Idempotency-Key`, 100-event maximum history response with truncation indication, and candidate minimum GitHub App permissions for issue reads, repository contents/branch writes, and PR writes (metadata read, issues read, contents write, pull requests write), subject to verifying actual API calls before implementation. Supplementary instruction text is optional and bounded at 16 KiB, matching the existing human-direction bound; it cannot override policy or authorize arbitrary commands. Define 256-bit random OAuth state with a 10-minute TTL and atomic one-time consumption; return the browser to GitHub via a redirect, with tokens never returned. For grant storage, use an external 32-byte deployment key with AES-256-GCM and AAD binding to principal/record; permit active plus prior decryption key IDs during atomic re-encryption rotation. No automatic relinking; require explicit operator revocation, and do not delete grants still referenced by active work.
- **Non-goals:** Implementing transport handlers, OAuth state persistence/exchange, GitHub App setup, access-token encryption, API versioning negotiation, generic task/command execution, queue provenance changes, cancellation/direction endpoints, worker execution, or modifying `/tmp/factory-rest-server-mvp-plan`.
- **Acceptance criteria:**
  1. The contract defines JSON request/response examples and success/rejection semantics for each route, including durable acceptance and stable request ID.
  2. Identity comes only from the bearer verifier; submit/status/history are isolated by authenticated principal and client-supplied identity is ignored/rejected.
  3. Idempotency is scoped to principal; exact retries return the same durable request, mismatched payload reuse conflicts, and no acknowledgment precedes durable queue persistence.
  4. History is capped at 100 events with a truncation indicator; request bodies, instruction size, and error responses are bounded; secrets and unnecessary issue/agent payloads are excluded.
  5. OAuth initiation is authenticated; public callback uses 256-bit random state bound to the principal, a 10-minute expiry, atomic single-use consumption, and explicit HTTPS callback URL; code-exchange failure is recoverable only by starting fresh, without unsafe replay. Relinking semantics, grant revocation, refresh failure, and external-key rotation are documented.
  6. GitHub permission entries are explicitly described as the minimum candidate set and require operation-level verification before implementation; merge/release/deploy are denied. Request source issue access is distinct from target repository authorization.
  7. Docs-only change preserves the separate design worktree; all described server behavior is labeled planned, not implemented; links resolve and `git diff --check` passes.
- **Status:** Contract drafted and published for review in PR #44; owner-authored follow-up additions clarify credential lifecycle and atomic persistence. No server behavior is implemented.
