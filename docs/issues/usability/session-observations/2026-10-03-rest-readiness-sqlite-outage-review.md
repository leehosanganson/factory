# REST readiness and SQLite outage review

- **Scope:** Checked whether runtime readiness probes on every non-health request contradict issue #90 and the current REST operations contract, especially for SQLite-lock reconciliation.
- **Evidence:** `docs/features/rest-server-operations.md` states `/readyz` returns 503 during store/provider failure and that job API routes fail closed with `503 not_ready` before processing. `docs/features/rest-server.md` likewise says readiness requires successful configured storage/provider probes. The accepted #90 wording requires readiness to fail closed on unavailable dependencies. `runtime.run` wires `SQLiteStore.Ping` and configured provider `Ping` into `ReadyError`, and `restapi.Handler.ServeHTTP` applies it before dispatching non-probe requests. Thus a failed probe yielding 503 instead of a route-specific 409 matches the documented contract; no runtime defect or spec change was justified.
- **Existing coverage:** `TestRunReadinessRecoversAfterProviderOutageAndBlocksAdmission` covers store/provider outages, readiness recovery, and blocked POST admission. The SQLite reconciliation process test verifies reconciliation remains unchanged during a SQLite write lock and succeeds after release. Existing docs and tests also cover startup failure, backup/restore, and aggregate operations status.
- **Explicit verification gap (not a demonstrated runtime defect):** #90's accepted criterion says health/readiness tests cover a SQL outage. `TestRunReadinessRecoversAfterProviderOutageAndBlocksAdmission` simulates storage Ping failure using a wrapper around SQLite; it does not induce real transient `SQLITE_BUSY`. The process E2E exercises a real SQLite write lock during reconciliation and verifies safe conflict/state preservation, but does not assert `/readyz` behavior under that lock. A route-matrix outage test is also absent: runtime outage coverage asserts POST admission, while handler tests cover representative POST/GET readiness gating. These are bounded test-coverage gaps only; current handler applies the gate globally and no wrong response was demonstrated. No spec change or candidate fix/test was made.
- **Verification:** Focused runtime/API/store tests passed. `make vet` and `make build` passed. `make test` initially failed because the environment's umask caused a filesystem mode assertion to observe mode 0750; rerunning as `umask 000; make test` passed. `git diff --check` passed.
