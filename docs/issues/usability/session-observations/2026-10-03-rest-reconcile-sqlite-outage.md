# REST reconciliation SQLite-outage session observation

- **Scope:** Extended the process-level uncertain-provider recovery E2E with a held SQLite `BEGIN IMMEDIATE` transaction during the authenticated operator reconciliation request. The lock is released before inspecting persisted job state and retrying.
- **Evidence:** The focused test first returned HTTP 500 with a safe generic body under the deterministic write lock, rather than the expected safe 409. After mapping persistence failure in the reconciliation callback to the existing ineligible-reconciliation error, focused runs passed with `-count=1` and `-count=3`.
- **Coverage:** The test checks failed/no-outcome state, absence of a reconciliation history event, the uncertain attempt, retained worktree, unchanged harness count and provider create/attempt counts, then successful explicit reconciliation after releasing the lock. It uses SQLite's cross-connection write lock rather than filesystem permission mutation, which can be unreliable across platforms and while a process holds an open DB connection.
- **Boundary/friction:** The test is gated to Linux/macOS like the surrounding process tests. While the SQLite write lock is held, job inspection may itself be blocked by SQLite's busy timeout, so the test validates state and recovery immediately after releasing the lock. The lock acquisition and recovery path passed repeated local runs; CI across supported platforms remains pending. No live provider or harness rerun occurs during reconciliation.
