# REST idempotency after restart HTTP E2E

- **Scope:** Extended `TestRESTServerProcessRunsConcurrentSQLiteJobsThroughProvider` to cleanly stop the server after successful SQLite/provider jobs, restart a new server process against the same DB, and replay one identical request through `POST /v1/jobs` with its original `Idempotency-Key`.
- **Evidence:** The replay returned HTTP 202 with `replayed=true` and the original ID; the HTTP job inspection retained succeeded status and the same provider outcome, while both fake-provider create records and publish-start records stayed unchanged. The focused E2E passed with `-count=1` and `-count=3`; `make vet` and `make build` passed. The first `umask 000 make test` run had one unrelated flaky status-invocation-count failure in `internal/factory`; a second full run passed all packages.
- **What worked/friction:** The existing process helper and fake-provider record made it possible to exercise durable idempotency at the actual HTTP boundary without production-code changes or live provider credentials. The test already checked direct store idempotency after restart, so the missing evidence was specifically the restarted server's HTTP path.
- **Boundary:** The fake provider verifies that the test server does not issue another fake create; it does not establish live GitHub behavior. This note records repository work, not a user report.
