# REST shutdown-cancellation E2E

- **Scope:** Extended the existing process-level SQLite request-to-PR E2E rather than duplicating its concurrency, publication, or workflow-failure coverage. The scenario admits a long-running workflow, waits for a start marker, sends SIGTERM to the real server process, reopens SQLite, and checks canceled status/history, no provider outcome, and retained workspace without completion metadata.
- **Evidence:** The new E2E assertion failed before the SQLite store correction: `Finish(StatusCanceled)` rejected shutdown because `Close()` had already disabled admission, leaving a running SQLite job in `running`. Allowing `Finish` while the database remains open resolves the race; the E2E then passes.
- **Behavioral distinction:** This verifies cooperative whole-server shutdown cancellation with durable SQLite records. It does not add or claim an HTTP per-job cancellation endpoint, nor automatic restart recovery of interrupted running jobs.
- **What worked/friction:** Existing process helper, custom harness fixture, and SQLite reopen path supported a focused test extension. The failing test exposed that the shutdown test seam needed to account for the store's distinction between stopping admission and remaining open for worker terminal writes. The child harness process exits on SIGTERM and left no observed `sleep 30` process after the test.
