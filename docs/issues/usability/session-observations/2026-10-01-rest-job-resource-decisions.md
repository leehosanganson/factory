# REST job resource and workspace policy decisions

- **Scope:** Updated the proposed REST job contract and execution-mode note with confirmed workflow, bounds, subprocess-output, and successful-workspace lifecycle choices. These are design decisions for downstream implementation, not evidence of implemented REST execution.
- **Confirmed job behavior:** One REST job runs Factory's existing multi-stage requirements, implementation, review, and documentation workflow plus configured verification checks. Multiple configured harness subprocesses may run within one job, bounded by a job-wide timeout. No branch push, PR creation/update, or PAT use is permitted. Default listener remains loopback; shared API-key holders are trusted with server-account authority and are not sandboxed.
- **Confirmed bounds:** 1000 retained records, 200 events per job, 262144 task bytes, and a 256 MiB aggregate manager budget using deterministic logical accounting of request/event string bytes plus fixed record/event allowances (not RSS). Capture at most 16 MiB of cumulative subprocess stdout/stderr per job across all stages and processes; continue draining after the cap and mark output truncated.
- **Confirmed result policy:** Keep successful workspaces for local inspection. Only protected completion metadata may establish eligibility after age is strictly greater than 24 hours; startup/periodic cleanup removes only well-formed recognized successes, rejects symlink/path escapes and unsafe races, and retains failed, canceled, unknown, orphaned, or unparseable results for inspection after restart. Missing or corrupt metadata fails closed.
- **Implementation handoff:** Define the fixed logical record/event accounting allowances explicitly and consistently account for admission, event updates, and eviction. The current server config schema's default task/output fields do not yet express the contract's task size, cumulative per-job output semantics, or manager budget; downstream config/runtime code must align those without presenting proposed values as existing defaults. Define protected completion metadata format, location, ownership/mode, and validation; use safe path operations/revalidation for sweeps. Keep manager state process-local; workspace cleanup metadata does not recover status or execution. Specify how output truncation is represented internally without exposing raw output via API history.
- **Friction/observation:** The REST contract already contained several agreed lifecycle and workflow decisions, while the proposed execution-mode and configuration notes used less specific resource wording/values. Recording the numeric limits and scope in the canonical contract and execution note reduces ambiguity for later implementation. No runtime behavior was exercised or validated in this documentation-only session.
