# Guarded GitHub App live-test infrastructure

- **What worked:** Existing `internal/restprovider.GitHubPublisher` provides an injectable HTTP client and already performs provider-side PR lookup after an ambiguous create response. A narrow transport seam now validates the configured GitHub API origin and exact repository/job/branch/base/body mapping, forwards the create once over a direct no-proxy connection, validates the returned PR/commit identity, and discards only that successful response; its test proves any second POST is refused.
- **Safety boundary:** Added only manual `workflow_dispatch` infrastructure with an explicit boolean confirmation, environment protection, exact non-secret repository allowlist and suffix validation, and bounded owned-resource cleanup. After clarification that the owner must be an approved organization, configuration now requires an exact approved organization variable and live API identity verification (`full_name`, owner login, and `owner.type == Organization`) before publish/cleanup. The workflow uses the explicit App installation ID and a short-lived repository-scoped token; it does not use PAT fallback or change runtime credential behavior.
- **Friction:** A generated configuration requires matching exact values in both the canonical `owner/repo` and separate owner/repository/allowlist variables. This duplication is deliberate defense in depth but creates more setup steps to audit. The initial workflow design minted once in each test job; review changed this to one mint-only workflow step and a masked same-job environment handoff. Test and cleanup code now consume the pre-minted token and cannot read the App private key or mint again.
- **Evidence boundary:** Local tests cover parsing, masking, token scope construction, exact create mapping, response-loss/reconciliation behavior, direct transport selection, and cleanup ownership. The dedicated installation/repository is not provisioned, so no live GitHub request was made and the workflow has not been validated against a live account. Issue #134 remains a prerequisite.
