# OAuth callback grant-persistence recovery design

- **Type:** Documentation follow-up from a proposed design gap; not a user-reported finding.
- **What worked:** Reviewing the callback and credential-custody contract against the durable single-use state-store behavior made the boundary clear: state is consumed before exchange, so a lost callback response cannot justify replay.
- **Evidence:** The REST API contract and credential-custody design now distinguish a valid persisted grant, confirmed absence from a healthy store, and unreadable/corrupt/key-inaccessible/uncertain grant data. A valid persisted record remains linked after a lost response; confirmed absence requires fresh authorization; unavailable evidence fails closed for operator reconciliation. Key-rotation text explicitly treats unreadability as uncertainty rather than absence. Review also caught and corrected an overbroad statement that an exchange failure necessarily left a principal unlinked; the design now states that no new grant is created and an existing grant remains unchanged.
- **Scope status:** Documentation-only on `docs/oauth-callback-recovery-contract`. No OAuth routes, provider calls, grant store, credential crypto, or runtime integration were added. A separate usability opportunity records the original gap.
- **Friction:** The former wording could lead readers to equate any callback failure after state consumption with absence of a grant, despite separately noting that persistence may have succeeded ambiguously. This edit replaces that ambiguity with explicit recovery outcomes.
