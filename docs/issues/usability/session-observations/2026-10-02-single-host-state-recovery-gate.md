# Single-host state retention and recovery gate

- **Type:** Design-gate observation for the proposed REST MVP; not a user-reported finding.
- **What worked:** Comparing the current `LocalWorkQueue` and `LocalIssueObservationStore` with the work feature documentation established the current local storage paths and recovery boundaries. Queue requests use per-record files and idempotent keys; issue observations are immutable by request/version, and lifecycle state can be reconciled from observation history when missing or stale. Existing atomic writes and local locking are useful implementation properties, but they do not establish backup, restore, host-loss, retention, or general corruption-recovery guarantees.
- **Design boundary:** The state-recovery gate records decisions required before server deployment or a worker relies on restart recovery. It distinguishes the queue and observation stores, names consistency/retention/backup/restore/migration/corruption questions, and does not choose retention durations or authorize pruning/compaction.
- **Scope status:** Documentation only. No runtime behavior, cleanup policy, backup implementation, or migration was added. The separate uncommitted REST MVP plan worktree was read-only and left unchanged.
- **Friction:** The REST MVP draft already mentions volume sizing, backup/restore, and recovery testing in its later deployment slice, but does not define the data-retention policy or the consistency and corruption decisions needed before that validation. Keeping the state-policy gate in the existing autonomous-work design avoids modifying the separate draft.
