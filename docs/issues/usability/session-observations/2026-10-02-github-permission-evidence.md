# GitHub App permission evidence audit

- **Type:** Research session observation for a REST MVP design gate; not a user-reported finding.
- **What worked:** GitHub's endpoint-specific REST docs and fine-grained permission map confirm that Get an issue accepts GitHub App user access tokens and requires Issues: read; Git-reference creation accepts user access tokens and requires Contents: write; pull-request creation/get accept user access tokens and require Pull requests: write/read respectively. GitHub's App authentication docs state user-token authority is limited by the user's and App's permissions/resources. The App-installation authentication page documents installation-token use for HTTPS-based Git access.
- **Evidence limits:** The fine-grained permission map establishes the issue read permission, correcting the earlier assumption that it was not visible. The cited HTTPS Git instructions cover installation access tokens, not the delegated user access token planned for this design. Do not infer user-token git clone/push support from REST endpoint support.
- **Scope status:** Update only the credential-custody design's evidence summary and references; do not select a final App permission set or implement Git transport.
- **Friction:** The readable issue-endpoint extraction omitted its fine-grained permission subsection. Fetching the raw documentation exposed both the endpoint's supported token types and Issues: read; the separate permission map corroborated Issues: read. SearXNG remained unavailable because its configured internal service address was blocked, but direct source retrieval resolved the issue-read question. User-token HTTPS Git support remains unresolved rather than inferred.
