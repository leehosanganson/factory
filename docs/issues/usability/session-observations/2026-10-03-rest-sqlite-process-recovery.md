# SQLite process-recovery verification

- **Scope:** Audited issue #90's documented SQLite restart behavior and existing process E2Es, then added an abrupt-process-restart scenario for one queued and one harness-blocked running job. The scenario verifies queued completion, unchanged running status/history, authenticated aggregate `recovery_needed`, exactly one interrupted-job harness invocation, and only one provider publication for the resumed job.
- **Verified defect and change:** The first process test timed out: after restart, the interrupted row consumed the only worker slot, preventing the queued row from running. SQLite claim capacity now excludes IDs classified as recovery-needed when that store opened; these rows remain `running` and visible for operator investigation. The new E2E passed three consecutive focused runs.
- **Checks:** `umask 000 && make test`, `umask 000 && make vet`, `umask 000 && make build`, and `git diff --check` passed.
- **Observation/friction:** The existing uncertain-provider E2E left two helper processes running after the full test suite; inspection of their environment tied them to that pre-existing test, and only those exact PIDs were terminated. The new test explicitly kills its blocked fake harness after killing the server. Consider tightening helper-process cleanup for the existing uncertain-provider test in a separate, scoped follow-up; no cause beyond the observed surviving processes was established here.
