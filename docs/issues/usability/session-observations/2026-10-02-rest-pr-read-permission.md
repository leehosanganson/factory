# REST API pull-request retrieval permission clarification

- **Type:** Evidence-based REST design correction; not a user-reported finding.
- **Evidence:** GitHub's official REST endpoint documentation lists GitHub App user access tokens as supported for `GET /repos/{owner}/{repo}/pulls/{pull_number}` and `POST /repos/{owner}/{repo}/pulls`. It specifies Pull requests: read (or Contents: read) for retrieval and Pull requests: write for creation. The selected REST contract had implied Pull requests: write also sufficed for retrieval, although that was not the GET endpoint's stated minimum. The combined App permission level still needs validation against both operations. The issue GET endpoint docs independently list GitHub App user tokens as supported and Issues: read as required. Keep token-type support distinct from permission requirements for each selected operation. [GitHub REST API — Pull requests](https://docs.github.com/en/rest/pulls/pulls#get-a-pull-request); [Get an issue](https://docs.github.com/en/rest/issues/issues#get-an-issue); [fine-grained token permission map](https://docs.github.com/en/rest/authentication/permissions-required-for-fine-grained-personal-access-tokens).
- **Scope status:** Clarified the operation-specific candidate permissions in the REST contract and credential-custody open gate. No final App permission set was chosen; delegated user-token HTTPS Git transport remains explicitly unverified. No OAuth, API, or runtime behavior was added.
- **Verification:** Fetched the official endpoint documentation and checked the GET and POST permission passages. Local links and `git diff --check` are checked before publication.
