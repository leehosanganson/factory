# Phase 5a: Kubernetes execution architecture

## Status and scope

This is an existing design proposal for a later, **opt-in experimental** Kubernetes execution mode, written before the North Star direction that users/operators own repository/model/harness risk and Factory makes no security-isolation guarantee. The proposal remains unimplemented and is not a current product commitment or deployment authorization. Its sandbox claims and requirements are not Factory guarantees or prerequisites. Any later Kubernetes execution capability must align with the current North Star trust boundary, require explicit operator configuration and acceptance of workload risk, and cannot be marketed as a Factory-provided sandbox. Factory currently runs local-process workers; a process, container, or Pod alone is not a security sandbox. Kubernetes mechanics may be operator-chosen hardening, but do not change the product boundary.

The first deployment shape is an operator-managed Kustomize base with explicit environment overlays. Execution images are immutable digest references. Each job's workflow execution and its later verification execution use separate, short-lived pods. Both pods must run under an explicitly configured gVisor- or Kata-backed `RuntimeClass`. If the class is missing, unusable, or rejected, the job fails closed; there is no ordinary-container fallback. The worker remains the trusted coordinator, retains provider credentials, and mediates a Pi-specific model gateway. Workflow and verifier pods receive no provider, Factory API, database, or model-provider credential.

This is an architecture boundary and set of gates, not a full executor or gateway implementation specification. Image internals, exact Kubernetes API versions, gateway wire format, cluster admission product, resource values, artifact quotas, and deployment topology details remain decisions to settle and test before implementation. No manifests, dependencies, or live-cluster verification are included here.

## Goals and compatibility

- Preserve the existing request, idempotency, verification-evidence, provider-outcome, cancellation, and inspection contract in the [REST job contract](rest-api-contract.md).
- Add a bounded remote execution option without allowing callers to select images, commands, paths, network access, or credentials.
- Separate untrusted workflow execution, verification execution, and the trusted model/credential mediation boundary.
- Keep local memory and SQLite modes usable with the current local executor. Kubernetes execution is opt-in and must not silently change their behavior.
- Support PostgreSQL-backed `factory worker` processes as the initial remote-worker integration point, subject to an explicit execution-mode compatibility gate. A workers-disabled PostgreSQL API control plane and separately launched workers may share the Store and existing `limits.workers` cap/configuration agreement, but this does not share worker-local workspaces or provide cross-worker recovery. Kubernetes is not a fleet coordinator, and PostgreSQL's current fenced claims do not themselves implement Kubernetes scheduling or fence external side effects.
- Preserve the rule that a configured provider operation must be confirmed and recorded before success. Factory does not merge, release, or deploy.

Mode selection is operator-owned configuration, never request data. Invalid or incomplete Kubernetes execution configuration must prevent that mode from starting or accepting execution; it must not fall back to local execution or a weaker Pod security profile. Local memory/SQLite deployments continue to select local-process execution explicitly or by their existing compatible default.

## Threat model

### Threat actors and untrusted inputs

Assume a job submitter may be malicious or compromised within the API role assigned to it. Repository content, issue/PR text, task text, dependency/build scripts, workflow-produced files, and model responses are untrusted. A compromised or malicious harness/model response may attempt to escape its intended workflow, exfiltrate repository data, misuse network access, forge verification evidence, or attack the worker, gateway, API server, Kubernetes API, or another job. A stale, partitioned, or compromised worker may race with a replacement worker. A cluster user able to alter admission policy, RuntimeClasses, node configuration, images, service accounts, or NetworkPolicies is a trusted infrastructure administrator and can defeat the intended boundary.

The design aims to constrain job code and agent activity to a per-job runtime sandbox, prevent job pods from obtaining durable service/provider credentials or Kubernetes authority, prevent one job from reading another job's workspace, and ensure a stale executor cannot commit durable Store mutations. PostgreSQL fencing protects Store mutations only; it does not atomically authorize or fence external Kubernetes API or provider side effects. It does not claim protection from a compromised node, kernel/runtime, cluster administrator, worker host/process, model gateway, or control-plane credential. gVisor/Kata availability and configuration are security prerequisites, not proof of isolation by themselves.

### Assets

- Job admission, ownership, state, idempotency, fencing tokens, and durable provider/verification evidence.
- Operator-approved repositories, source snapshots, task and issue context, generated patches, and verifier results.
- Git provider tokens and database DSN, plus Factory API caller credentials.
- Model-provider credentials and model request/response content at the trusted gateway boundary.
- Kubernetes API credentials, worker identity, image provenance/digests, RuntimeClass and admission/network policy.
- Audit events and operational metadata, which must not disclose secret or raw-content assets.

### Trust boundaries

1. **API/control plane to worker:** authenticated bounded jobs and durable state. The API credential is not included in a job payload sent to execution pods.
2. **Worker to Kubernetes API:** trusted worker identity creates/observes/cancels only owned job resources and performs fixed artifact operations. It has no cluster-admin authority and does not expose a general command proxy.
3. **Worker to workflow pod:** per-job untrusted repository/task/workflow inputs and bounded result artifacts. The workflow process executes repository-controlled content inside the required sandbox; its pod has no provider/API/database credentials.
4. **Workflow pod to model gateway:** separate, narrow, authenticated-by-workload or otherwise job-bound protocol to a **trusted Pi-specific gateway**. The gateway is an explicit trust boundary: it handles model-provider credentials and can observe prompts/repository context and generated content. The workflow pod may send only bounded model requests; it cannot ask the gateway to forward arbitrary tools, network requests, credentials, or secrets.
5. **Worker/provider and gateway/provider boundaries:** provider credentials remain in worker/gateway-side trusted components and are used only for configured operations. The workflow pod and verifier pod never receive them.
6. **Worker to verifier pod:** after workflow completion, the worker transfers validated candidate artifacts into a new credential-free verifier sandbox. Verification runs independently of the workflow process and cannot inherit its process memory, writable filesystem, or claimed evidence.

The model gateway is not inside the workflow sandbox. It is a trusted service and must not be described as an untrusted pass-through or as part of the verifier. The verifier is a separate sandbox, not an independent correctness authority: checks can still be incomplete, maliciously chosen by trusted operator config, or insufficient to prove correctness.

## Execution shape

1. The API admits a normal REST job. A PostgreSQL worker claims it using the existing database ownership/fencing contract. Local memory and SQLite jobs continue through the local executor; this design adds no cross-process Kubernetes claim semantics to those backends.
2. The worker resolves the immutable configured image digests, checks the configured RuntimeClass and cluster prerequisites, and creates one workflow Pod for the job with server-derived identity and limits. Admission policy verifies the security profile before scheduling. A prerequisite or admission failure is a terminal execution failure or an explicit operator-recovery condition; it never triggers a weaker retry.
3. The worker sends only the bounded job context and repository snapshot through the defined artifact protocol. The workflow Pod runs the configured Pi workflow in an isolated checkout. Pi model calls use the narrow trusted gateway protocol. No provider publication occurs in this Pod. Repository and workflow artifacts remain ephemeral and are transferred only as needed for the next phase.
4. On workflow completion, the worker stops/collects the workflow Pod, validates its output as untrusted, then creates a separate verifier Pod for the same job and attempt generation. The verifier receives only a validated source tree and operator-configured check definition, runs checks without model access or credentials, and returns bounded evidence. A failed or canceled workflow does not get promoted to a successful verifier result.
5. The worker validates and records bounded verification evidence through the durable Store under the active fencing generation. It performs configured branch/provider operations outside both job pods using worker-held credentials and existing live-attempt provider handling, subject to the proven stale-worker side-effect gate described above. This does not provide Factory-mediated recovery after workspace/artifact loss. A fence check around a provider request does not prevent a stale request from taking effect. If a provider or Kubernetes side effect may have occurred but its outcome is uncertain, the worker must not convert that uncertainty to success or automatically replay the operation; it preserves the unresolved state for operator investigation. Factory-mediated cross-worker reconciliation is unavailable when the ephemeral workspace/artifacts are lost.
6. The worker removes per-attempt ephemeral pods, streams, and scratch after terminal state and bounded result handling. Cleanup failure is observable and cannot turn a failed/uncertain job into success. No remote recovery artifacts are retained.

The one-workflow-Pod-per-job rule does not combine workflow and verification into one sandbox. The verifier is a distinct Pod and trust domain, created as a later phase, with its own execution limits and RuntimeClass requirement. Exact pod naming, Job-vs-Pod API choice, and whether a Kubernetes Job controller is used are implementation decisions; none may weaken per-attempt identity, deletion, fencing, or fail-closed admission.

## Kubernetes admission and sandbox requirements

Admission is a defense-in-depth gate. The worker performs preflight checks, and cluster-side admission must independently reject nonconforming job Pods. Exact policy engine and policy syntax are open decisions; a local-only preflight is not a substitute.

Required checks include:

- The configured RuntimeClass exists and maps to an approved gVisor or Kata runtime on eligible nodes. The Pod explicitly selects it; a missing class, unsupported node, scheduling failure, or runtime startup failure is surfaced and never retried without the required runtime.
- Every container image, including workflow, verifier, init/helper, and any injected sidecar, is an allowed immutable `image@sha256:<digest>`. Tags, mutable references, image substitution, unapproved ephemeral containers, and implicit service-mesh/debug injection are rejected. Digest provenance/signature policy and approved registry are deployment gates.
- Pod labels/annotations, service account, namespace, owner/job/attempt identity, volume set, RuntimeClass, security context, resource bounds, and network policy match the worker's narrowly defined template. Caller-supplied pod fields are impossible.
- Non-root UID/GID, read-only root filesystem, no privilege escalation, all Linux capabilities dropped, seccomp profile, and restricted Pod Security admission are enforced. Privileged mode, host PID/IPC/network, host paths, device access, unsafe sysctls, and unapproved Linux options are denied. Exact UID/GID, seccomp profile, and writable scratch arrangement must be proven compatible with selected images/runtimes before selection.
- Resource requests/limits, ephemeral storage, active deadline, process count where enforceable, and maximum pod count/concurrency are bounded by operator policy. Limit values and behavior under node pressure/OOM are implementation gates; configuration values must not be represented as hard guarantees until tested.
- The job service account is not mounted into job pods; `automountServiceAccountToken` is disabled. No API token, DB secret, provider token, host credential, or broad namespace secret is mounted or projected.
- Only expected containers and volumes exist. No arbitrary sidecars, projected credentials, PVC claims, or mutable shared volumes are allowed unless explicitly reviewed as part of the security design.

### Network, storage, and filesystem

Default-deny ingress and egress apply to both job pod classes. Workflow egress is limited to the specific gateway endpoint and any explicitly approved in-cluster artifact/control endpoints required by the protocol; direct model-provider, GitHub/provider, Internet, DNS, metadata-service, and cross-namespace access are denied unless a narrowly justified exception is designed and tested. The verifier has no model gateway, provider, API, database, or general Internet egress. NetworkPolicy enforcement by the selected CNI, DNS behavior, gateway identity/mTLS, and egress policy coverage are live-cluster gates; policies that are not enforced fail the deployment gate.

Each phase uses per-job/per-attempt scratch storage with an explicit size limit and no cross-job sharing. All repository snapshots, workflow artifacts, verifier inputs/results, and temporary workspaces are **ephemeral**: no persistent volume or hostPath is exposed to job pods, and no shared durable artifact store or cross-worker artifact recovery is in scope. During a live attempt, the trusted worker may transfer bounded outputs between isolated workflow/verifier pods and retain only the transient material needed to validate results and complete configured provider publication. PostgreSQL remains authoritative for job state, bounded verification evidence, and provider-attempt/outcome metadata; it does not preserve workspace contents. Ephemeral bytes are deleted at terminal cleanup and may be lost immediately if the pod, worker, or node is lost. A recovery artifact format, S3-compatible storage, workload identity federation, object publication, and database/object-store consistency protocol are explicitly deferred. If worker/pod loss or a transfer failure leaves execution or provider effects uncertain, do not replay or reassign the job, do not fabricate success, and do not attempt Factory-mediated cross-worker provider reconciliation; preserve the durable unresolved state and require operator investigation using independent provider/cluster records. This sacrifices recovery artifacts and automated reconciliation after loss. It is an accepted limitation for this phase, not a claim that investigation or recovery is guaranteed.

## Credentials and model gateway

- API bearer credentials, database DSNs, Git/provider tokens, and Kubernetes API credentials remain outside both workflow and verifier Pods. Provider publication and reconciliation are worker-mediated and use the configured provider adapter; credential delivery to a job pod is prohibited.
- The initial model integration is Pi-specific. Pi in the workflow sandbox addresses a bounded trusted gateway; it does not receive a provider key or arbitrary model endpoint credentials. The gateway uses operator-managed model-provider credentials outside job pods and enforces configured model/provider selection and limits.
- The gateway protocol must not be a generic proxy. Requests and responses have explicit schemas, maximum encoded and decoded byte sizes, maximum message/turn or call counts, per-call and whole-job deadlines, and bounded concurrent streams. It rejects unknown fields, unsupported operations, oversized inputs/outputs, malformed frames, and unrecognized model/tool names. Exact bounds and Pi integration point are implementation gates.
- The gateway does not offer arbitrary tool execution, arbitrary URL fetch, generic HTTP forwarding, shell, provider writes, Kubernetes access, secret lookup, or secret forwarding. No ambient credentials are copied into model context or tool results. Secrets and prompt text are redacted from ordinary logs; bounded security audit records contain classifications and identifiers, not bodies.
- Worker/gateway authentication must bind requests to a job and attempt generation, enforce authorization and quotas, and prevent one job from impersonating another. Pod identity mechanism, key rotation, TLS, and request replay resistance remain decisions to validate before deployment.

## Worker-to-pod protocol and artifact handling

Kubernetes exec streams are the initial transport for sending input and retrieving output artifacts. Exec is available only to the trusted worker using a fixed helper/protocol in the pinned image; it is not exposed as a caller API and does not accept caller-selected commands or argv. The fixed helper and argv are a trusted worker-code invariant, not an RBAC enforcement boundary: permission to use `pods/exec` does not constrain the command or argv a permitted worker can request. Worker code review, immutable pinned images, and narrowly scoped worker identity are therefore required; do not claim that RBAC enforces the fixed-helper restriction. The implementation must define a versioned, length-delimited stream framing protocol before coding. It must not rely on stdout text parsing or an unbounded archive extraction tool.

The protocol must provide:

- Explicit operation and job/attempt correlation IDs, stream direction, artifact/phase identity, byte lengths, and cryptographic digest. Multiplexed channels carry independent framed messages with unique correlation IDs and bounded per-channel and aggregate buffers; unknown IDs, duplicate completion, wrong attempt, frame reordering where disallowed, malformed lengths, and trailing data fail closed.
- Bounded request/response and artifact sizes at every layer (worker, Kubernetes exec transport, helper, decompressor, and disk). Length checks occur before allocation or extraction. Compression, if selected, has separate compressed and expanded limits and a ratio cap.
- Bounded open/read/write/idle/whole-operation timeouts, cancellation propagation, and close semantics. On cancellation, the worker stops streams and requests pod termination; it does not treat a partially transferred artifact as complete. Stream disconnection, exec session loss, or ambiguous final acknowledgment is an uncertain transfer: do not treat it as success or blindly retry; preserve unresolved durable state for independent operator investigation if the transient artifact is unavailable.
- No arbitrary command, shell, arbitrary network forwarding, or secret forwarding. Worker uses only fixed protocol operations such as initialize input, fetch completed artifact, and terminate/inspect phase.

Repository trees and returned artifacts are untrusted on both sides of the stream. Before extraction or use, validate normalized relative paths; reject absolute paths, `..`, NULs, duplicate/case-colliding names where relevant, reserved control paths, and paths escaping the designated root. Reject symlinks, hard links, devices, FIFOs, sockets, sparse/special entries, unsupported file types, and unsafe permissions unless an explicitly reviewed format safely represents a narrowly required type. Enforce file-count, per-file, total uncompressed byte, and nesting/path-length caps. Do not follow links during validation or extraction. Verify declared and computed digests and an overall manifest digest; a digest proves transfer integrity, not trustworthiness or correctness.

Write artifacts into a new private staging directory on the worker, validate completely, fsync where supported, then atomically publish/rename into the attempt's workspace only if it remains within the expected root and attempt. Never merge partial output into a trusted checkout. A crash before atomic publication leaves disposable staging data. After publication, the manifest/digest and active generation may be checked only while the artifact remains available to the live attempt; if worker loss makes it unavailable, preserve unresolved state for operator investigation without replay or cross-worker restoration. Artifact ownership, cross-filesystem atomicity, platform portability, archive format, and worker-side path-race defenses must be tested and selected before implementation.

## Lifecycle, fencing, cancellation, and recovery

Kubernetes Pod status is execution evidence, not the durable job state. The durable Store remains authoritative. Proposed mapping:

| REST job state | Kubernetes interpretation |
| --- | --- |
| `queued` | No execution Pod is authorized yet. A claim must succeed before resource creation. |
| `running` | A current fenced worker attempt is active; its workflow/verifier phase may be provisioning, running, transferring, or cleaning up. Phase summaries remain bounded safe metadata. |
| `succeeded` | Workflow and independent configured verification completed, required provider result was confirmed, and all required outcome/evidence writes succeeded under the current fence. |
| `failed` | A definitive execution/verification/provider failure occurred and was durably recorded; preserve inspectable evidence according to policy. |
| `canceled` | Cancellation was honored before any uncertain provider side effect; the worker has stopped the execution and recorded terminal state. Cancellation request alone is not terminal state. |
| recovery-needed / uncertain | Existing durable running state remains unresolved after worker/pod/stream loss or ambiguous side effects; do not invent success, canceled, or retry. Expose through existing recovery inspection semantics where supported. |

Every resource and protocol operation is bound to job ID, attempt generation, and worker ownership token/identity. PostgreSQL fencing serializes and protects durable Store mutations only; it does not fence Kubernetes API or provider effects. A check of the current fence immediately before or after an external action is not atomic with that action: a worker can become stale between the check and a Kubernetes Pod create/delete or provider branch/PR operation. Pod labels are selectors, not fencing authority. The conservative proposed protocol below makes retries and deletion safer, but does not establish external-effect fencing or prove zero stale effects.

### Proposed stale-worker handling protocol (not fencing proof)

This is a proposed conservative protocol for an experimental implementation, not a claim that Kubernetes names, delete preconditions, or the PostgreSQL lease form an atomic cross-system transaction.

- **Attempt identity and create retries:** derive deterministic resource names from the job ID, monotonically increasing attempt generation, and phase (workflow or verifier). Before creating, GET that exact name. If it exists, validate its namespace, UID/owner relationship, job ID, generation, phase, immutable image/runtime/security identity, and other server-derived fields against the expected attempt; only an exact match may be treated as a retry of the same generation. A mismatch blocks and requires investigation; do not adopt, mutate, or delete it as if it were owned. If absent, create with that name and on timeout/ambiguous response GET and validate the same object before deciding disposition. Named API objects support idempotent create/retrieval, but this makes same-generation create retries reconcilable only; it is not a lease check, does not stop a delayed old create, and does not link Kubernetes state atomically to PostgreSQL. See [Kubernetes API concepts](https://kubernetes.io/docs/reference/using-api/api-concepts/).
- **Exact-object deletion:** first observe and validate the exact attempt Pod, retaining its UID and resourceVersion. Delete that exact named Pod with both UID and resourceVersion preconditions from the observation. A precondition mismatch must be treated as conflict (HTTP 409): re-observe and do not delete a replacement object based on stale observations. This prevents a stale delete request from deleting a different replacement object; it does not fence whether the old worker is authorized to request deletion or prevent other Kubernetes effects. See [Kubernetes DeleteOptions](https://kubernetes.io/docs/reference/kubernetes-api/common-definitions/delete-options/).
- **No overlapping generations:** under the current contract, never reclaim/replay an interrupted `running` job and never start a newer generation while an older attempt's Pod or external side effects may still be active. Require observed termination of every Pod for that generation and resolution of side-effect uncertainty before any explicitly authorized future generation; otherwise keep the job blocked/recovery-needed for operator investigation. A lease expiry or a missing Pod observation alone is not proof that a delayed create cannot still arrive.
- **Bounded stale sandbox:** workflow/verifier Pods receive no provider, database, Factory API, Kubernetes, or model-provider credentials. The trusted gateway validates job ID, attempt generation, and expiry on every request and rejects stale generations. This bounds gateway access by stale Pods but cannot stop sandbox-local computation already underway; it is not a complete kill/fence mechanism.
- **Provider writes and uncertainty:** persist the provider attempt identity before issuing a provider write, as the current executor does. Only a worker holding the current valid generation may initiate the call, but a check-before-call is not atomic with the provider operation. If the lease is lost, cancellation occurs, the response is lost, or the result is otherwise uncertain after the attempt is recorded, leave the operation unresolved and do not retry the write. Cross-worker/provider reconciliation is out of scope for this phase because workspace/artifacts are ephemeral and no recovery worker is provided. Operators investigate provider state independently using configured provider/cluster records; Factory does not expose a recovery artifact or automatically poll/reconcile. One lookup that finds no result is not proof that a delayed in-flight write cannot still arrive. Do not report terminal success or automatically issue another provider write while unresolved.

**Explicit limit and selected product policy:** standard Kubernetes named-object/create and delete-precondition mechanics plus a PostgreSQL lease do **not** prove zero stale external effects. The user approved the conservative policy: no reassignment or replay while an older attempt or side effect may remain active; persist unresolved state; do not replay or reassign; and require independent operator investigation when uncertainty remains. This policy explicitly accepts that it is **not zero-stale-write prevention**: a delayed provider write may still land, including after an independent lookup found no result. Zero stale provider writes remain unproven. Recovery artifacts are ephemeral and may be lost; operators investigate uncertain outcomes independently. The policy decision does not make execution eligible: delayed-call fault tests, explicit ephemeral-artifact loss handling, worker lifecycle validation, and the live-cluster gate remain mandatory. If a provider-side zero-write guarantee later becomes a product requirement, block Kubernetes execution until a provider-side conditional/fencing mechanism is proven.

A queued job must be claimed before creating a Pod. Cancellation while queued prevents creation. For running jobs, cancellation targets that job/attempt only: persist the request, cancel active exec streams, request deletion/termination of owned workflow or verifier Pods, wait for observed termination or a bounded uncertainty deadline, then record the terminal outcome. Repeated cancellation is idempotent. If provider publication may have occurred, cancellation cannot claim `canceled`; preserve the attempt for operator investigation. When ephemeral artifacts are lost, Factory-mediated reconciliation is unavailable. A provider operation remains outside the Pod. Because artifacts are ephemeral, loss after a potentially effective provider write leaves no Factory-mediated cross-worker reconciliation path; operator investigation is required.

Job deadline includes provisioning, all gateway/model calls, artifact transfers, workflow, verifier, provider operations, and cleanup policy boundaries as explicitly allocated. Pod `activeDeadlineSeconds` and worker context deadlines are coordinated but not treated as equivalent; exact grace periods and cleanup timeout are open decisions. On deadline, cancel streams and terminate Pods, discard ephemeral artifacts according to cleanup policy, and record failure only after the executor has a definitive outcome. Worker process interruption or loss of database connectivity must stop new work and avoid unfenced writes.

If a Pod disappears, is evicted, or its exec stream ends unexpectedly, the worker first checks the current durable attempt and Kubernetes resource identity. It must not recreate/replay the same phase or job merely because a Pod is absent. A known pre-execution provisioning failure may be classified failed only when no workflow/provider side effect could have occurred and that decision is atomically recorded. Any uncertainty after execution may have started leaves the durable job `running`/recovery-needed for operator investigation; ephemeral artifacts may already be lost and the job must not auto-replay. Uncertain Kubernetes or provider side effects cannot be converted to success or replayed. No watcher, lease-expiry handler, pod cleanup task, scheduled poller, or recovery worker may automatically reassign the attempt or start reconciliation. Cross-worker recovery and Factory-mediated provider reconciliation are not supported in this phase; the operator must investigate independently. Provider reconciliation is not inferred from Pod labels or transient artifact presence.

PostgreSQL workers may resume only jobs still safely queued under current Store rules; an interrupted running execution is not automatically replayed. Memory and SQLite modes retain their current local-process lifecycle/recovery behavior. Kubernetes mode does not introduce transparent failover. Kubernetes execution artifacts are ephemeral, so cross-worker restoration and Factory-mediated reconciliation after worker loss are unavailable; a shared PostgreSQL Store preserves lifecycle/provider metadata, not the workspace. Unresolved jobs require operator investigation and are not replayed automatically.

## Kustomize deployment and least privilege

The experimental deployment should be opt-in and separate from existing local server/worker configuration. Provide a reviewed Kustomize base and overlays, not a default install. The overlay chooses namespace, pinned images, RuntimeClass name, resource/quota bounds including ephemeral scratch, gateway endpoint/trust, network policy, and external secret references. Secrets are supplied through the operator's established secret mechanism, not committed into Kustomize literals or placed in Pod specs for job workloads. No Kubernetes manifests are created by this task.

- API/control-plane and worker service accounts are distinct. API authority is limited to the selected Store/network requirements. The worker has only the namespaced verbs/resources required to create/get/watch/delete the Factory-owned execution resources and use exec/attach for those resources; no cluster-wide list/watch, secret read, pod privilege mutation, or broad exec is granted. Exact RBAC verbs and subresources are a security review gate.
- Job pods use a dedicated service account with no token mount, no RoleBinding, and no secret access. Workflow and verifier pod templates are separate, immutable policy shapes. Admission controls disallow caller mutation and injection.
- Namespace ResourceQuota/LimitRange and worker concurrency limits cap pods, CPU/memory, and ephemeral storage. Cluster nodes must advertise the selected RuntimeClass; node selectors/tolerations and disruption handling are explicit. Exact scheduling and quota strategy remain deployment decisions.
- NetworkPolicies isolate API, worker, gateway, Store/provider egress, and job Pods. Worker egress is limited to Kubernetes API, the configured durable Store, the provider, and necessary telemetry as approved. Workflow egress is gateway-only; verifier egress is denied by default. Verify the selected CNI enforces policy.
- Config/image overlays use digest-pinned references, not tags. A digest change is an explicit reviewed rollout. Config map changes cannot alter a running attempt's effective image/runtime security profile.
- Pod TTL/garbage collection is not trusted as the source of job retention or reconciliation. Worker cleanup is generation-aware, and orphan sweeping may delete only resources whose ownership and terminal/cleanup policy have been verified. This does not retain ephemeral workspaces/artifacts; operators may separately inspect durable job metadata and independently available cluster/provider records.

API and worker topology should follow current server behavior: an all-in-one PostgreSQL server may execute jobs locally unless workers are disabled; separately launched PostgreSQL workers share durable claims and the global `limits.workers` cap, not their local workspaces. Kubernetes execution in this phase keeps execution artifacts ephemeral and does not provide cross-worker workspace recovery, an S3-compatible store, or a recovery worker. PostgreSQL records durable job/attempt state and provider identity, but not workspace bytes. Unresolved jobs require operator investigation and are not replayed or automatically reconciled. This is an explicit recovery limitation, not a fleet coordinator or failover capability. Rollout, upgrade, and rollback behavior for jobs in flight, database schema/config compatibility, and safe image rollback require an operational design before production use.

## Audit and observability

Record bounded structured events for job/attempt, worker identity, phase, resource identity, RuntimeClass, image digest, admission decision category, transfer byte counts/digests, verifier check labels/outcomes, cancellation/deadline, pod termination/cleanup, and recovery disposition. Audit events support correlation but are not authorization. Persist only fields already permitted by the REST contract; expose no raw prompts, task/repository contents, model bodies, artifact paths, token values, DSNs, API keys, environment dumps, exec command text, or raw pod logs through job APIs or routine logs.

Logs and metrics use bounded labels; never use task text, repository paths, credentials, or unbounded job payload fields as labels. Errors are sanitized. Pod events/logs may contain untrusted data and must be access-controlled, retention-limited, and excluded from caller-facing status. Capture only bounded excerpts if a future operational feature explicitly permits them; this architecture does not add a log/transcript API. Audit sink durability, retention, access, and cluster audit-log configuration remain deployment gates. Metrics should distinguish provisioning, workflow, gateway, transfer, verifier, provider, and cleanup latency/failure without implying correctness or sandbox health.

## Acceptance and security tests

Before enabling even the experimental overlay, tests must cover the following. Unit/contract tests and policy tests can run without a live cluster; they do not satisfy the live-cluster gate below.

1. **Selection and compatibility:** default/local memory, SQLite, and PostgreSQL paths retain existing executor behavior; Kubernetes mode requires explicit opt-in and valid worker/PostgreSQL setup as selected. Invalid configuration, unavailable runtime class, missing digest, failed admission, or unsupported runtime must fail closed without local/ordinary-container fallback.
2. **Admission policy:** reject tags, mutable image references, missing/wrong RuntimeClass, privileged/host access, extra containers/volumes, service-account tokens, secrets, caller-controlled metadata, unbounded resources, and altered security contexts. Verify allowed workflow and verifier templates remain distinct and both require the sandbox runtime.
3. **RBAC and network:** policy tests prove the worker can manage only intended owned resources and cannot read Secrets or perform cluster-wide operations; job service accounts have no authority. Test default-deny egress and deny attempts to reach Store, provider, Kubernetes API, metadata endpoints, arbitrary DNS/Internet, or other jobs. Verify gateway-only workflow access and no gateway access from verifier.
4. **Gateway:** schema/limit tests reject oversized, malformed, unknown, replayed, cross-job, and unauthorized requests; enforce response bounds, deadlines, cancellation, concurrency caps, and redaction. Prove no arbitrary tool, URL, command, network, provider, or secret-forwarding operation exists. Pi adapter conformance tests must exercise normal, streaming, malformed, timeout, cancellation, and gateway-loss paths. Exact Pi protocol integration is a prerequisite, not assumed.
5. **Artifact safety:** adversarial fixtures cover traversal, absolute paths, links, special files, duplicates, file/count/expanded-size limits, digest mismatch, truncation, reordered/duplicated frames, correlation mismatch, disconnects, cancellation mid-transfer, staging crash, atomic publication, and stale-generation rejection. Confirm no partial tree reaches the verifier or provider workspace.
6. **Execution/lifecycle:** exercise workflow success/failure, independent verifier results, deadline, cancellation in each phase, worker death, database partition, Pod eviction/deletion, exec disconnect, ambiguous completion, and cleanup failure. Verify stale Store writes are fenced; uncertain running jobs are not reclaimed/replayed; terminal success requires recorded evidence and confirmed provider result; provider uncertainty remains unresolved under the rules above. Do not infer that Store fencing prevents stale external writes.
7. **Stale-worker side effects:** inject delayed create after lease expiry, delayed delete against a newer object (the precondition must conflict/return 409 and must not delete it), duplicate same-generation create, rejection of an old gateway generation, lease loss immediately before and during provider write, provider response loss, and an in-flight provider write delayed until after an independent operator lookup. Assert no newer generation starts while the old Pod/side effects may be active, no false terminal success, no automatic provider write retry, mismatched resources are not adopted/deleted, and uncertainty remains durable with operator follow-up required. Include the accepted case where the delayed write lands after the independent lookup and verify it is not mistaken for zero-write prevention. These tests characterize and bound behavior; they cannot establish provider-side fencing where the provider has no fencing/idempotency mechanism. A PostgreSQL Store test with an injected channel/result can verify stale durable writes and recovery state only; it does not exercise a provider request in flight. Separate executor/provider-adapter fault injection must delay an actual fake provider write across lease loss and reconciliation, and must explicitly demonstrate that the write may land after a no-match lookup without causing a retry or false success.
8. **Redaction:** inspect captured worker, API, gateway, Kubernetes event, and test logs for task/prompt bodies, raw artifacts, commands, paths, API keys, provider/model credentials, and DSNs. Verify caller-facing job state remains bounded and sanitized.
9. **End-to-end disposable-cluster tests:** validate actual admission policy, RuntimeClass behavior, network enforcement, RBAC/subresources, ephemeral storage quotas, image pull/digest enforcement, cancellation/termination, bounded artifact transfer and ephemeral cleanup/loss semantics, worker lifecycle, exact-object delete preconditions, and stale-worker fault scenarios using the intended supported Kubernetes version/runtime/CNI combination. Verify that loss does not trigger replay or automatic reconciliation and leaves durable unresolved state. Shared artifact-store/recovery-worker tests are deferred and are not acceptance claims for this phase.

### Live-cluster gate

No live Kubernetes behavior is verified by this document or by repository-only tests. Before enabling the experimental Kustomize overlay, an operator must record the cluster/runtime/Kubernetes versions, gVisor/Kata RuntimeClass implementation and node coverage, admission engine and effective policies, CNI/NetworkPolicy enforcement, RBAC review, digest/provenance process, secret delivery, ephemeral quotas/loss behavior, explicit no-replay/no-cross-worker-reconciliation handling, worker lifecycle results, and results of the disposable-cluster security and delayed-call stale-worker fault tests. Failure or unknown status for any required isolation, admission, network, credential, or exact-object deletion property blocks rollout. The user has approved the conservative no-reassignment/no-replay policy and explicitly deferred Factory-mediated recovery artifacts; it accepts that artifacts may be lost and a delayed provider write may still land, and does not establish zero stale writes. Operators investigate uncertain outcomes independently. Fault tests and all other gates remain required, and the document does not claim execution is eligible yet. If zero stale provider writes later becomes a product requirement, no rollout is eligible until provider-side fencing/conditionality is proven. A live cluster is required to validate Kubernetes behavior; the first deployment must be explicitly approved, isolated, non-production, and use disposable repositories/credentials. It is a validation exercise, not evidence of production readiness, and none of these mechanics alone proves zero stale external effects.

## Recommended first implementation slice

**Status: partially implemented (configuration compatibility stub only; no executor/resources).** The operator-owned `execution.mode` selector accepts `local` or `kubernetes`; omission defaults to local. Existing local memory, SQLite, and PostgreSQL configurations remain valid. Kubernetes selection with memory or SQLite is rejected because PostgreSQL is required; Kubernetes selection with PostgreSQL is rejected explicitly as not implemented. The server and worker validate config before opening runtime resources, so this selector cannot fall back to local execution. No Kubernetes security settings are accepted or implied.

This implements only the approved compatibility gate, not the broader initial Kubernetes worker integration proposed here. Complete Kubernetes security configuration, worker-specific eligibility, resource creation, executor behavior, and external-side-effect handling remain unimplemented gates. Shared artifact storage and cross-worker recovery are intentionally deferred rather than required for this phase. The selector establishes a fail-closed boundary before any such work.

## Non-goals and unresolved gates

This phase does not implement a generic Kubernetes executor, model gateway, arbitrary remote command API, issue scheduler, workflow catalog, new job type, fleet manager, shared database/workspace failover, workflow checkpointing, automatic replay of interrupted running jobs, caller-visible logs, provider operations in job pods, merge/release/deployment, or general-purpose Kubernetes API. It does not replace Pi or local memory/SQLite development and test modes.

Before implementation, resolve and approve: supported cluster/Kubernetes versions; exact RuntimeClass distributions and node attestation assumptions; admission-policy engine and mutation policy; image build, signing/provenance, update, and rollback controls; workflow/verifier image contents and pinned helper protocol; Pi gateway integration and model credential ownership; request/response byte/turn/concurrency budgets; bounded ephemeral artifact framing and path semantics; per-phase resource/deadline values; service-account/RBAC rules; CNI, DNS, TLS/workload identity, and egress policy; exact-generation naming, GET/create validation, and UID/resourceVersion-preconditioned Pod deletion; no-reassignment/no-replay behavior and durable blocked/recovery-needed disposition when ephemeral artifacts are lost; generation-aware orphan cleanup; durable audit destination; delayed-call fault-test criteria; and the exact experimental live-cluster acceptance procedure. Shared durable artifacts, cross-worker restoration, and Factory-mediated reconciliation after worker loss are explicitly deferred, not prerequisites for this phase; if recovery is reconsidered, propose it separately and request approval before selecting an artifact/database protocol. Kubernetes preconditions and PostgreSQL Store fencing do not resolve provider-side stale writes. The conservative provider-uncertainty policy is approved, but its required implementation and validation gates remain open; a provider-side zero-write guarantee is a blocker if that requirement is later adopted. Unknown answers are rollout blockers, not defaults to guess.
