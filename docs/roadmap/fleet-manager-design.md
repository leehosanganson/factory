# Fleet coordination — later direction

The current REST job-service implementation has no horizontally scaled controller replicas, Thread model, or multi-unit scheduler. The target Factory-unit MVP described in [factory-unit-mvp.md](factory-unit-mvp.md) introduces a single logical control plane whose controller replicas may scale horizontally, a simple scheduler for user-pinned or eligible Factory-unit assignment, and local Factory-unit coordination adapters. That initial topology is not a general fleet coordinator, remote placement system, or high-availability guarantee. The current service still provides an in-memory development backend, optional SQL persistence for restart durability, and required PR create/update through a configured repository provider.

Do not design fleet ownership or reassignment until durable job state, worker fencing, recovery, and uncertain provider-write reconciliation have been implemented and validated. A container restart or expired lease is not proof that a previous worker stopped or that replay is safe. Containers and Nix shells are not security sandboxes.

Later fleet scheduling across multiple logical control planes, remote placement, or independently scaled controller roles requires a separate proposal covering shared durable coordination, authenticated unit identity, fencing, resource placement, artifact/log retention, and recovery. A context-aware coordinator behind a Factory-unit adapter may coordinate only local execution unless a future reviewed design explicitly expands that authority. Users/operators own repository and model/harness threat risk; Factory makes no sandbox or security-isolation guarantee. See the [roadmap](roadmap.md), [Factory-unit MVP architecture](factory-unit-mvp.md), and [REST job contract](rest-api-contract.md) for canonical direction.
