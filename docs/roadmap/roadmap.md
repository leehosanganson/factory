# Factory roadmap

## Product direction

Factory is a RESTful job service for agent-driven repository work. A client submits a bounded job request; Factory executes it against an operator-approved repository, records its lifecycle, and creates or updates a pull request through the configured code-repository provider. When publication is configured, PR creation/update is required for Job success. Humans retain authority over merge, release, and deployment. Verification evidence and limitations remain visible; agent or process success is not an independent correctness verdict.

The target REST job MVP has one service and one Job lifecycle—not separate REST-task and autonomous issue-to-PR products. The Factory Worker MVP adds an operator/developer workbench, user-facing Threads, Auto or named-Worker routing, recurring schedules, and authenticated multi-source webhook admission as described in [Factory Worker MVP architecture](factory-unit-mvp.md). It does not include Agent routing or remote Worker host/harness provisioning. Each Worker uses its operator-configured default harness/profile. Its core job path is:

**request → durable admission → bounded execution → verification → provider PR create/update → inspectable outcome**

Issue details may be supplied as context or admitted by the implemented separate poller into the same job lifecycle; issue polling/reconciliation is not a separate MVP. Provider-neutral interfaces keep repository hosting replaceable; each supported provider must implement the same scoped branch/PR behavior.

## Persistence and runtime

The service starts with a simple in-memory backend for local development, demonstrations, and tests. It is intentionally volatile: process restart loses jobs, history, idempotency records, and active execution state. It must never be described as durable across restarts.

The direct-request Thread API slice is implemented: authenticated `GET /v1/threads` lists redacted bounded summaries with immutable admission pagination; `POST /v1/threads` atomically admits a Thread with its initial Job; `GET /v1/threads/{id}` returns ordered membership and lifecycle-derived status; `POST /v1/threads/{id}/jobs` appends a member Job; and bodyless `POST /v1/threads/{id}/complete` records owner-controlled closure without changing status or member Jobs. Member admission is serialized with completion, and new members are rejected after closure. These routes run on memory, SQLite, and PostgreSQL stores. The authenticated `GET /v1/notifications` provides an owner-filtered in-product Done inbox, with no external sender or read-ack state. This partial implementation does not complete the broader Thread target: one optional GitHub `issues.labeled` webhook is implemented, but the shared multi-source webhook contract and controller/Worker placement remain tracked in [#301](https://github.com/leehosanganson/factory/issues/301) and [#297](https://github.com/leehosanganson/factory/issues/297), respectively. The webhook requires PostgreSQL storage and database-registered ownership of its exact source/trigger-label pair, verifies the signed raw event and configured source/trigger label, and atomically admits into the existing Thread/Job lifecycle. The shared PostgreSQL owner registry prevents the webhook and issue poller from owning the same exact pair in that database; SQLite webhook admission is unavailable. See [GitHub issue webhook](../features/github-issue-webhook.md) for its limits. See the [Thread model contract](thread-model.md).

Persistence is behind a backend interface. Optional SQLite provides restart-persistent state for a single server; optional PostgreSQL is also implemented in the canonical REST Store/runtime and can be shared by an API control plane and separately launched `factory worker` processes. Both fail closed when explicitly configured storage is unavailable. Queued durable jobs resume after restart; interrupted running jobs are retained for operator investigation and are not replayed. Eligible durable jobs support explicit disposition or read-only provider observation when the required persisted provider attempt and retained workspace are available; a workers-disabled PostgreSQL control plane cannot perform the lookup. PostgreSQL uses database-backed worker ownership/leases and a shared execution cap, but does not provide workflow checkpoints or a fleet coordinator. Memory mode is volatile and is not an implicit fallback when a configured durable store fails.

The all-in-one server with bounded local workers remains the current default deployment. PostgreSQL also supports separately launched workers sharing the canonical Store; this does not yet provide the future controller/Worker architecture described in the [Factory Worker MVP direction](factory-unit-mvp.md). That direction starts with horizontally scalable replicas of one logical controller and Auto or named-Worker placement. A pinned Worker does not silently fall back. Each Worker uses its operator-configured default harness/profile; Agent routing is not in the MVP. The initial deployment is a one-host validation topology, not high availability. Repositories, harnesses, credentials, and bounded job policy remain operator-configured.

The canonical PostgreSQL Store/runtime and separate worker command are implemented, but this does not establish high availability or general fleet management. Do not assume automated primary failover/promotion, multi-primary operation, production RPO/RTO, replication, or recovery guarantees. Connection loss or ambiguous transaction outcomes are unknown, not proof of rollback; operators must establish authoritative durable state before permitting further attempts or provider writes. The separately documented [PostgreSQL ownership deployment contract](postgresql-ownership-deployment-contract.md) concerns the isolated ownership-protocol test fixture; it is not a statement that the canonical REST Store/runtime is unimplemented. See also the [worker identity and credential contract](worker-identity-credential-contract.md), the [worker recovery/cancellation contract](worker-recovery-cancellation-contract.md), and the [attempt workspace/provider-write contract](attempt-workspace-provider-write-contract.md).

Factory does not provide or guarantee sandboxing, security isolation, or protection from repository-controlled or model/harness behavior. Users and operators are responsible for assessing and accepting those risks in their deployment environment. Operators continue to control the approved repositories, enabled harness profiles, credentials, and bounded job policy; requests cannot select arbitrary configured executables, repositories, or credentials. Actual process access to network and local authority remains dependent on the execution account and deployment environment. Worker identity/authorization, attempt ownership, recovery/cancellation, job-data integrity, and provider-write correctness remain separate lifecycle and policy requirements, not evidence of containment. The [optional host-isolation reference](oci-sandbox-host-contract.md) is not a Factory support claim or prerequisite for job execution or the Factory Worker MVP.

## Pull-request and human boundary

Creating or updating a PR with the configured code-repository provider is a required part of a successful implementation job, not an optional publication feature. A job must not report success until the provider operation is confirmed and its PR identity/URL is recorded. Retries after timeouts or process interruption must reconcile live provider state before repeating a write; uncertain outcomes are surfaced for recovery rather than blindly creating another branch or PR.

Factory may commit and push only within the job's approved repository and scope. It does not merge PRs, release artifacts, or deploy software. Approval gates, policy escalation, bounded retries, visible verification results, and safe cancellation preserve human control without making PR creation itself an approval decision.

## Current implementation versus target

Factory has a Go CLI and a local REST job server. The server accepts authenticated bounded requests, executes configured workflows in isolated workspaces, and exposes status/history. It supports volatile memory or optional SQLite/PostgreSQL persistence and configured GitHub PR publication. Queued durable jobs resume after restart; interrupted `running` jobs remain for operator investigation without replay. Authenticated operator routes can disposition eligible interrupted durable jobs only when no provider attempt/outcome exists, or make a read-only provider observation for eligible interrupted/failed durable jobs when their persisted attempt identity and retained workspace are available. The observation does not record an outcome or success because a matching PR does not prove the earlier write has stopped. A workers-disabled PostgreSQL control plane cannot perform the lookup. These actions do not rerun the harness or write to the provider. PostgreSQL supports shared Store/runtime use by the API and separately launched workers, with database-backed ownership and a shared worker cap; this does not add a fleet coordinator or HA guarantee. Setup, readiness, recovery, and operational-status guidance is documented. Backup and portable recovery-bundle commands remain SQLite-only and do not include separate workspace trees. Merged PR #128 adds deterministic tests of the production GitHub adapter against GitHub REST-shaped `httptest` responses, including accepted-create/lost-response reconciliation; process-level provider recovery tests use a fake provider. Neither establishes behavior against a live GitHub account. Merged PR #155 adds a manual-only, guarded live App harness, and merged PR #157 adds atomic compare-and-swap cleanup; these do not establish a live account/provider validation run. That run remains unverified and owner-gated by open issue #134; #135 is also open. Merged PR #131 adds SQLite backup/restore process E2E coverage, not a production restore drill. Merged PR #133 superseded closed issue #117 and adds startup logging of the selected persistence mode after listener readiness; it does not expose the SQLite path or secrets. No automatic recovery/replay or workflow checkpoints for interrupted running work, or fleet coordinator, is provided. PostgreSQL worker ownership/leases are implemented but do not make a fleet manager. These limits are not separate product directions. The separate CLI now provides first-use `factory doctor` diagnostics (#138) and a process test for detached-job reconnect via fresh `get`/`logs` commands with retained recovery artifacts (#140); this evidence does not mean Factory replaces Pi or completes the broader primary-engine vision.

The CLI's `implement`, `tidy`, `monitor`, detached jobs, and `work` commands remain available and are documented under [implemented features](../features/README.md). They are current interfaces, not additional MVP architectures. The local `work` issue-observation commands do not start an autonomous issue-to-PR worker. The future Thread model for user requests and multi-source authenticated webhook ingress is not current behavior; the only implemented webhook is the optional GitHub `issues.labeled` adapter described above. Scheduled Tasks and scheduled Jobs remain outside Threads in that target model. Its contract is in [Thread model](thread-model.md), with implementation tracked in [#301](https://github.com/leehosanganson/factory/issues/301).

## Delivery sequence

The current REST foundation and the future Factory Worker MVP are distinct. For the remaining target MVP, use the dependency order in [Factory Worker MVP architecture](factory-unit-mvp.md): safety and attempt-integrity gates (#248–#261); canonical Thread lifecycle (#301); Worker registration/routing and default harness (#297); recurring schedule/backend access alignment, including operator management of all schedules with creator attribution preserved (#332, #333, #339); shared authenticated multi-source webhook admission (#301, with the current GitHub-only implementation in #306); operator/developer workbench (#358); then the measured pilot (#299). Each step depends on its predecessor's accepted API and durable contract. Webhook authentication/event envelope, Worker registration trust/capacity, and unavailable pinned-Worker behavior remain open design decisions and must be resolved before the corresponding implementation. This is a dependency sequence, not a release commitment.

1. **Define durable job semantics (implemented):** canonical job/request and lifecycle, backend interface, idempotent admission, bounded history, retention, cancellation, and conservative recovery behavior. PostgreSQL worker ownership/leases are implemented; workflow checkpoints and fleet coordination are not provided.
2. **Add SQL persistence (implemented):** SQLite and PostgreSQL stores persist jobs, events, idempotency, and execution state; configured-store failures fail closed. Concurrent admission and restart behavior are tested. Queued jobs resume after restart; interrupted running jobs remain inspectable and are not replayed.
3. **Complete REST job operation (implemented):** status/history, safe errors, limits, readiness, and recovery semantics are available across the supported backends; SQLite and PostgreSQL retain inspectable records across restart. #124 adds authenticated operator actions for explicit interrupted-job disposition and read-only provider observation without replay; an observation records a matching provider result separately and does not resolve the job or record an outcome.
4. **Add repository-provider operations (implemented):** configured GitHub operations publish a scoped branch and create/update a PR, recording the confirmed PR identity. Eligible interrupted-running or terminal failed SQLite/PostgreSQL jobs with persisted provider identity and retained workspaces support read-only provider observation on a worker-enabled runtime. This does not resolve uncertain writes or report success; they are not blindly retried.
5. **Integrate and validate the request-to-PR path (core gates implemented; validation remains):** process-level tests cover request-to-PR execution, concurrent admission, duplicate/idempotent requests, shutdown cancellation, queued-job restart resumption, interrupted-running retention, and fake-provider failure/lost-response and explicit operator reconciliation. Merged PR #128 adds production GitHub adapter tests against GitHub REST-shaped `httptest` endpoints for an accepted PR create with a lost response, failed lookups, exact read-only reconciliation mapping, token redaction, and no duplicate write. These deterministic tests do not establish live GitHub account/repository behavior; a live account/provider run remains unverified and owner-gated by open issue #134 (#135 is also open). Merged PR #155 adds a manual-only, guarded live App harness, while merged PR #157 adds atomic compare-and-swap cleanup; neither constitutes that live account/provider validation. Automatic recovery/reconciliation and workflow checkpoints for interrupted running jobs, and fleet coordination, remain unimplemented; PostgreSQL worker ownership/leases are implemented.
6. **Operational hardening (core documentation and support implemented; validation remains):** setup/configuration and security boundaries, health/readiness, SQLite recovery and retention, a consistent database backup command with restore guidance, and authenticated count-only operational status are documented and shipped. PR #131's backup/restore process E2E does not constitute a production restore drill. Merged PR #133 superseded #117 and adds startup logging of the selected persistence mode after listener readiness; it does not disclose the SQLite path or secrets. Database backup excludes separate workspaces. This is operational support, not general metrics/telemetry; unresolved interrupted work still needs operator investigation.

These are dependency gates, not dates. The optional `factory issue-poller` process admits exact-allowlisted GitHub issue source/versions atomically as one Thread with one canonical Job in the same PostgreSQL Store. It does not create a webhook endpoint or separate execution lifecycle. The shipped GitHub `issues.labeled` webhook is one narrow adapter, using the shared PostgreSQL intake-owner registry; SQLite webhook admission is unavailable. The target MVP's generic webhook is a separate shared authenticated inbound contract for multiple configured sources, stable source-event deduplication, and mapping/admission into canonical Threads/Jobs. It does not allow arbitrary user transforms. Authentication and event-envelope details remain open design choices; no provider-specific contract is implied. The operator/developer workbench may inspect and manage these configured integrations but does not provision hosts or install harnesses. The broader Worker/Thread/Job ingress model, controller replicas, and simple scheduler are described in [Factory Worker MVP architecture](factory-unit-mvp.md); those capabilities are not implied by this REST slice. Context-aware Worker coordination, multi-harness execution per Job, and Kubernetes remain later capabilities.

## Explicit exclusions

- No merge, release, or deployment authority.
- No general arbitrary-command endpoint or caller-selected executable.
- No Factory-provided sandbox, security-isolation, or hostile-code containment guarantee for agent, process, Nix shell, container, or Kubernetes execution.
- No separate REST-task and autonomous issue-to-PR execution lifecycles; the implemented poller feeds the same REST job queue. The target Worker/Thread model groups Jobs from direct requests and configured webhook sources; one optional GitHub `issues.labeled` webhook is already implemented, but the shared authenticated multi-source contract remains future work. Scheduled Jobs remain outside Threads.
- The current REST service has no controller fleet. The target Worker MVP adds one logical controller with horizontally scalable replicas and simple Auto/named-Worker placement; this does not imply autoscaling, remote host/harness provisioning, or high availability.

See the [REST job contract](rest-api-contract.md) for API and reliability requirements, [Factory Worker MVP architecture](factory-unit-mvp.md) for target controller/Thread/Job/Worker boundaries, [Thread model](thread-model.md) for ingress, membership and completion semantics, [execution modes](execution-modes.md) for the server/executor boundary, the [Kubernetes execution proposal](kubernetes-execution-design.md) for an unimplemented operator-configured deployment design that does not establish a Factory security guarantee, the [PostgreSQL ownership deployment contract](postgresql-ownership-deployment-contract.md) for the isolated protocol's test-only boundary and failover prohibitions, the [worker identity and credential contract](worker-identity-credential-contract.md), the [worker recovery/cancellation contract](worker-recovery-cancellation-contract.md), the [attempt workspace/provider-write contract](attempt-workspace-provider-write-contract.md), and the [optional host-isolation reference](oci-sandbox-host-contract.md) for operator deployment-hardening considerations; it is not a Factory prerequisite or support contract.
