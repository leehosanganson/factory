# Factory roadmap

## Product direction

Factory is a RESTful job service for agent-driven repository work. A client submits a bounded job request; Factory executes it against an operator-approved repository, records its lifecycle, and creates or updates a pull request through the configured code-repository provider. Humans retain authority over merge, release, and deployment. Verification evidence and limitations remain visible; agent or process success is not an independent correctness verdict.

The target MVP has one service and one job lifecycle—not separate REST-task and autonomous issue-to-PR products. Its core path is:

**request → durable admission → bounded execution → verification → provider PR create/update → inspectable outcome**

Issue details may be supplied as context or admitted by the implemented separate poller into the same job lifecycle; issue polling/reconciliation is not a separate MVP. Provider-neutral interfaces keep repository hosting replaceable; each supported provider must implement the same scoped branch/PR behavior.

## Persistence and runtime

The service starts with a simple in-memory backend for local development, demonstrations, and tests. It is intentionally volatile: process restart loses jobs, history, idempotency records, and active execution state. It must never be described as durable across restarts.

The first direct-request Thread API slice is implemented in the current development branch: authenticated `POST /v1/threads` atomically admits a Thread with one initial Job; `GET /v1/threads/{id}` returns its ordered membership and lifecycle-derived status across memory, SQLite, and PostgreSQL; `POST /v1/threads/{id}/complete` explicitly records owner-controlled closure without changing status or member Jobs. New member admissions are serialized with completion and rejected after closure. This does not complete the broader Thread target. Webhook/provider ingress remains tracked in [#301](https://github.com/leehosanganson/factory/issues/301). The owner-filtered in-product Done notification inbox is implemented; it has no external sender or read-ack state. See the [Thread model contract](thread-model.md).

Persistence is behind a backend interface. Optional SQLite provides restart-persistent state for a single server; optional PostgreSQL is also implemented in the canonical REST Store/runtime and can be shared by an API control plane and separately launched `factory worker` processes. Both fail closed when explicitly configured storage is unavailable. Queued durable jobs resume after restart; interrupted running jobs are retained for operator investigation and are not replayed. Eligible durable jobs support explicit disposition or read-only provider reconciliation when the required persisted provider attempt and retained workspace are available; a workers-disabled PostgreSQL control plane cannot perform reconciliation. PostgreSQL uses database-backed worker ownership/leases and a shared execution cap, but does not provide workflow checkpoints or a fleet coordinator. Memory mode is volatile and is not an implicit fallback when a configured durable store fails.

The all-in-one server with bounded local workers remains the default deployment. PostgreSQL also supports separately launched workers sharing the canonical Store, without a fleet coordinator or a guarantee of high availability. Repositories, agent harness, credentials, and limits remain operator-configured. Local-process execution and containers are not security sandboxes. Fleet coordination, remote placement, and broader hosting layers are not MVP prerequisites.

The canonical PostgreSQL Store/runtime and separate worker command are implemented, but this does not establish high availability or general fleet management. Do not assume automated primary failover/promotion, multi-primary operation, production RPO/RTO, replication, or recovery guarantees. Connection loss or ambiguous transaction outcomes are unknown, not proof of rollback; operators must establish authoritative durable state before permitting further attempts or provider writes. The separately documented [PostgreSQL ownership deployment contract](postgresql-ownership-deployment-contract.md) concerns the isolated ownership-protocol test fixture; it is not a statement that the canonical REST Store/runtime is unimplemented. See also the [worker identity and credential contract](worker-identity-credential-contract.md), the [worker recovery/cancellation contract](worker-recovery-cancellation-contract.md), and the [attempt workspace/provider-write contract](attempt-workspace-provider-write-contract.md).

Untrusted repository work has no implemented sandbox. The [OCI sandbox host contract](oci-sandbox-host-contract.md) is a candidate Linux-first design/validation boundary only; it does not make containers, rootless runtimes, or Kubernetes Pods a security guarantee. Strict isolated execution remains prohibited until a supported host profile and enforceable controls are implemented and tested alongside worker ownership, cancellation, and trusted credential/provider handoff.

## Pull-request and human boundary

Creating or updating a PR with the configured code-repository provider is a required part of a successful implementation job, not an optional publication feature. A job must not report success until the provider operation is confirmed and its PR identity/URL is recorded. Retries after timeouts or process interruption must reconcile live provider state before repeating a write; uncertain outcomes are surfaced for recovery rather than blindly creating another branch or PR.

Factory may commit and push only within the job's approved repository and scope. It does not merge PRs, release artifacts, or deploy software. Approval gates, policy escalation, bounded retries, visible verification results, and safe cancellation preserve human control without making PR creation itself an approval decision.

## Current implementation versus target

Factory has a Go CLI and a local REST job server. The server accepts authenticated bounded requests, executes configured workflows in isolated workspaces, and exposes status/history. It supports volatile memory or optional SQLite/PostgreSQL persistence and configured GitHub PR publication. Queued durable jobs resume after restart; interrupted `running` jobs remain for operator investigation without replay. Authenticated operator routes can disposition eligible interrupted durable jobs only when no provider attempt/outcome exists, or reconcile eligible interrupted/failed durable jobs through read-only provider confirmation when their persisted identity and retained workspace are available. A workers-disabled PostgreSQL control plane cannot run reconciliation. These actions do not rerun the harness or write to the provider. PostgreSQL supports shared Store/runtime use by the API and separately launched workers, with database-backed ownership and a shared worker cap; this does not add a fleet coordinator or HA guarantee. Setup, readiness, recovery, and operational-status guidance is documented. Backup and portable recovery-bundle commands remain SQLite-only and do not include separate workspace trees. Merged PR #128 adds deterministic tests of the production GitHub adapter against GitHub REST-shaped `httptest` responses, including accepted-create/lost-response reconciliation; process-level provider recovery tests use a fake provider. Neither establishes behavior against a live GitHub account. Merged PR #155 adds a manual-only, guarded live App harness, and merged PR #157 adds atomic compare-and-swap cleanup; these do not establish a live account/provider validation run. That run remains unverified and owner-gated by open issue #134; #135 is also open. Merged PR #131 adds SQLite backup/restore process E2E coverage, not a production restore drill. Merged PR #133 superseded closed issue #117 and adds startup logging of the selected persistence mode after listener readiness; it does not expose the SQLite path or secrets. No automatic recovery/replay or workflow checkpoints for interrupted running work, or fleet coordinator, is provided. PostgreSQL worker ownership/leases are implemented but do not make a fleet manager. These limits are not separate product directions. The separate CLI now provides first-use `factory doctor` diagnostics (#138) and a process test for detached-job reconnect via fresh `get`/`logs` commands with retained recovery artifacts (#140); this evidence does not mean Factory replaces Pi or completes the broader primary-engine vision.

The CLI's `implement`, `tidy`, `monitor`, detached jobs, and `work` commands remain available and are documented under [implemented features](../features/README.md). They are current interfaces, not additional MVP architectures. The local `work` issue-observation commands do not start an autonomous issue-to-PR worker.

## Delivery sequence

1. **Define durable job semantics (implemented):** canonical job/request and lifecycle, backend interface, idempotent admission, bounded history, retention, cancellation, and conservative recovery behavior. PostgreSQL worker ownership/leases are implemented; workflow checkpoints and fleet coordination are not provided.
2. **Add SQL persistence (implemented):** SQLite and PostgreSQL stores persist jobs, events, idempotency, and execution state; configured-store failures fail closed. Concurrent admission and restart behavior are tested. Queued jobs resume after restart; interrupted running jobs remain inspectable and are not replayed.
3. **Complete REST job operation (implemented):** status/history, safe errors, limits, readiness, and recovery semantics are available across the supported backends; SQLite and PostgreSQL retain inspectable records across restart. #124 adds authenticated operator actions for explicit interrupted-job disposition and read-only reconciliation without replay.
4. **Add repository-provider operations (implemented):** configured GitHub operations publish a scoped branch and create/update a PR, recording the confirmed PR identity. Eligible interrupted-running or terminal failed SQLite/PostgreSQL jobs with persisted provider identity and retained workspaces can be reconciled through read-only provider confirmation on a worker-enabled runtime; uncertain writes are not blindly retried.
5. **Integrate and validate the request-to-PR path (core gates implemented; validation remains):** process-level tests cover request-to-PR execution, concurrent admission, duplicate/idempotent requests, shutdown cancellation, queued-job restart resumption, interrupted-running retention, and fake-provider failure/lost-response and explicit operator reconciliation. Merged PR #128 adds production GitHub adapter tests against GitHub REST-shaped `httptest` endpoints for an accepted PR create with a lost response, failed lookups, exact read-only reconciliation mapping, token redaction, and no duplicate write. These deterministic tests do not establish live GitHub account/repository behavior; a live account/provider run remains unverified and owner-gated by open issue #134 (#135 is also open). Merged PR #155 adds a manual-only, guarded live App harness, while merged PR #157 adds atomic compare-and-swap cleanup; neither constitutes that live account/provider validation. Automatic recovery/reconciliation and workflow checkpoints for interrupted running jobs, and fleet coordination, remain unimplemented; PostgreSQL worker ownership/leases are implemented.
6. **Operational hardening (core documentation and support implemented; validation remains):** setup/configuration and security boundaries, health/readiness, SQLite recovery and retention, a consistent database backup command with restore guidance, and authenticated count-only operational status are documented and shipped. PR #131's backup/restore process E2E does not constitute a production restore drill. Merged PR #133 superseded #117 and adds startup logging of the selected persistence mode after listener readiness; it does not disclose the SQLite path or secrets. Database backup excludes separate workspaces. This is operational support, not general metrics/telemetry; unresolved interrupted work still needs operator investigation.

These are dependency gates, not dates. The optional `factory issue-poller` process admits exact-allowlisted GitHub issue source/versions atomically as one Thread with one canonical Job in the same PostgreSQL Store. Durable issue provenance is the dedupe authority; a bounded label ledger tracks label removal. This does not create a separate execution queue or lifecycle, and it adds no HTTP/webhook endpoint. Further issue reconciliation, provider events, additional code hosts, fleet coordination, reusable workflow catalogs, and deployment orchestration remain future possibilities.

## Explicit exclusions

- No merge, release, or deployment authority.
- No general arbitrary-command endpoint or caller-selected executable.
- No claim that an agent, process, Nix shell, or container is sandboxed.
- No separate MVP for autonomous issue polling; the implemented poller feeds the same job lifecycle.
- No fleet coordinator or distributed broker requirement for the initial service; separately launched PostgreSQL workers are supported without those guarantees.

See the [REST job contract](rest-api-contract.md) for API and reliability requirements, [execution modes](execution-modes.md) for the server/executor boundary, the [PostgreSQL ownership deployment contract](postgresql-ownership-deployment-contract.md) for the isolated protocol's test-only boundary and failover prohibitions, the [worker identity and credential contract](worker-identity-credential-contract.md), the [worker recovery/cancellation contract](worker-recovery-cancellation-contract.md), the [attempt workspace/provider-write contract](attempt-workspace-provider-write-contract.md), and the [OCI sandbox host contract](oci-sandbox-host-contract.md) for candidate host prerequisites and refusal boundaries.
