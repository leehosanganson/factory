# Worker identity and credential contract

## Status and current boundary

**Worker session registration and advisory heartbeat are now implemented for separately launched PostgreSQL `factory worker` processes; authenticated remote job claims, assignment, and ownership mutation are not implemented.** The ordinary REST runtime still uses in-process workers by default. The separate PostgreSQL ownership protocol in `internal/jobs/postgres_ownership.go` remains test-only; it is not yet the runtime worker claim protocol and provides no production recovery or reassignment.

This contract defines the broader identity and ownership boundary required for a future independent worker protocol. The shipped session slice does not expose jobs to the Worker API, change claim ownership, or authorize production deployment of a distributed fleet.

## Recommended architecture

Use **mutual TLS from a trusted worker supervisor to a control-plane worker API**. The control plane authenticates the client certificate, maps its public-key identity to a stable operator-provisioned worker principal and authorization policy, and obtains worker identity from that mapping—not from request JSON, headers, a database row, or a worker-selected ID. The supervisor generates a fresh cryptographically random boot ID at process startup. The control plane binds the authenticated principal and boot ID to a single active supervisor session and returns a session-bound capability for subsequent claim/heartbeat/mutation requests. All request authorization additionally checks job, generation, active session, and the opaque per-attempt fencing token.

The worker supervisor is a trusted protocol component; repository-controlled harnesses and job code run with the execution environment's available authority, without a Factory-provided security-isolation guarantee. Users/operators accept that repository and model/harness risk. Workers do not connect directly to PostgreSQL and do not intentionally receive database credentials, control-plane signing keys, another worker's credentials, or provider credentials. The control plane remains the only component that writes ownership state. Keeping credentials outside the harness reduces deliberate exposure, but does not guarantee hostile code cannot obtain authority available to the execution account. If future architecture requires direct worker-to-PostgreSQL connections, that is a separate design decision: it must specify database-authenticated principal mapping, strict least-privilege grants/stored procedures, session pooling behavior, credential revocation, and proof that no worker can bypass protocol predicates. Shared database credentials plus caller-supplied worker IDs do not meet this contract.

A boot ID is an incarnation label, not an authenticator. It must be generated by the trusted supervisor, bound to its authenticated principal/session, never accepted as proof by itself, and never reused after process restart. A credential copied to another machine remains a credential compromise; the server must not treat boot IDs as hardware attestation or proof of process uniqueness.

## Principal and authorization model

- Provision a stable, unique worker principal per independently revocable worker installation or supervisor slot. The principal is operator-managed and is not a human submitter identity. A human-readable worker name is display metadata only.
- Map a validated certificate public-key fingerprint or equivalent cryptographic identity to that principal in operator-controlled control-plane configuration/registry. Do not accept a principal ID supplied by the worker as an authorization decision. Certificate subject/SAN strings are not trusted identity unless explicitly matched to the provisioned credential record.
- Authorize only enabled worker principals with the worker role. Submitter/operator API bearer tokens are not worker credentials and cannot claim worker work. Worker credentials cannot call operator routes, list arbitrary jobs, change server configuration, or publish to a provider.
- Every claim is bound to the authenticated principal and the server-issued boot session. Every heartbeat, state/progress update, cancellation acknowledgement, evidence/artifact reference, and finish must be fenced by current job ID, monotonic generation, session, and opaque per-attempt token. Never permit caller-supplied worker/boot fields to override the authenticated context.
- When the future claim protocol is implemented, the control plane must return only work assigned through that protocol, with the minimum request/snapshot fields needed by the supervisor. It must not expose global queues or other jobs' private data through that API. The current session listener returns no job data or claims. The supervisor must not intentionally pass session credentials or raw API responses that include unrelated jobs to the harness. This protocol-level separation is not a guarantee that local code cannot access other authority available to the execution account.
- Record the authenticated principal and boot ID in immutable attempt history for audit. Never persist certificate private keys, raw bearer/session credentials, or the per-attempt fencing token in append-only history or user-visible job output.

## Credential issuance, storage, rotation, and revocation

- Issue a distinct client certificate/private key (or equivalent short-lived asymmetric credential) per worker principal through an operator-controlled CA/secret-management process. Define a bounded certificate lifetime, subject-to-principal mapping, renewal authority, and audit record. Do not make self-service enrollment or accept arbitrary CA chains.
- Store private keys in an operator-managed secret facility intended to be readable only by the worker supervisor's service identity. Do not intentionally put them in repository checkouts, container images, task payloads, process arguments, harness environment, logs, or shared filesystem mounts. The supervisor must not pass its TLS connection, key file descriptor, Unix socket, or session capability into repository-controlled workload processes. These custody practices reduce deliberate exposure; Factory does not guarantee hostile code cannot obtain authority available to the execution account.
- Rotation is overlap-based and explicit: provision and validate the replacement credential for the same principal, confirm the supervisor can establish an authenticated session with it, then revoke the old credential. At each point, reject unknown/expired credentials; do not load a partially parsed registry or silently fall back to an old shared secret. Control-plane config reload must be atomic or fail readiness while preserving the last known-good verifier according to an explicit policy.
- Revocation immediately blocks new sessions and new claims. Existing sessions must fail authorization at the next authenticated request (including renewal and every mutation), not merely at lease expiry. Revoke does not rewrite attempt history or imply the running process stopped. Mark any active attempt suspect, signal the trusted supervisor through a separate authenticated revocation channel where available, and block replacement/provider writes until #260 stop-proof and #261 side-effect gates are satisfied. If a credential may be compromised, operator must also isolate/stop the host and rotate any exposed secrets; server-side revocation cannot prove host process death.
- Bound session duration and require fresh authentication/renewal. Session capabilities are short-lived, scoped to the authenticated principal and boot ID, kept only in trusted supervisor memory, redacted from diagnostics, and unusable for a different boot or worker. If the control plane cannot confirm session state or revocation due to outage/ambiguous DB result, fail closed: no claim or side effect; do not treat an unconfirmed revocation as process stop.
- Audit issuance, successful authentication, failed authentication (without credential material), rotation, disable/revoke, principal mapping changes, session registration/retirement, and operator recovery decisions. Logs contain stable principal and event metadata only; never certificate/private-key bytes, tokens, or raw authorization headers.

## Session and attempt behavior

1. The Worker loads operator-configured client certificate/key and server CA paths, opens an HTTPS mTLS connection to the control plane, and registers its fresh process boot ID before the coordinator starts claiming from the shared PostgreSQL store. The control plane validates the client chain, validity period, revocation/disable state, and exact credential-to-principal mapping before authorizing a session.
2. The control plane atomically records the session and returns a short-lived capability. The Worker keeps the capability in process memory and periodically heartbeats it; heartbeat updates advisory presence and extends the same capability's expiry while it is still valid. A conflicting session for the same worker slot is rejected; it is not silently allowed to steal active ownership.
3. Session registration and heartbeat do not claim jobs. A future claim protocol must atomically allocate the job's next generation and bind owner principal, boot ID, and opaque attempt token. Retries with ambiguous transaction/response outcomes must not create a second attempt or assume absence; consult authoritative state under #258's no-failover restrictions or leave unresolved for operator review.
4. The current session listener authenticates the heartbeat via the mTLS-mapped principal and bearer capability, and has no job mutations. Future worker-originated job requests must derive principal and boot identity from the authenticated session, then check current generation/token/lease. A stale, expired, revoked, or mismatched session cannot mutate. Authentication success alone never bypasses attempt fencing.
5. The Worker does not retire its session on shutdown or heartbeat loss, because those events do not prove local/external processes stopped. An active session with expired capability may block a new boot until explicit authenticated operator retirement. On crash, partition, lost commit acknowledgement, or unproved stop, ownership is suspect; heartbeat loss and capability expiry are not reassignment authority. Recovery details are specified by #260 and remain unimplemented.

## Failure and privacy requirements

- Unknown, disabled, revoked, expired, malformed, or incorrectly mapped credentials fail closed with a generic authentication error; do not echo presented identities, certificates, secrets, or whether another principal exists.
- Authentication/authorization denial must occur before returning job payload, task text, status, history, artifacts, or side-effect outcomes. A worker cannot probe another worker's job by changing IDs or boot labels.
- Certificate rotation/revocation may block legitimate work; prioritize preventing credential reuse over availability. Never fall back to the API's legacy shared key, a caller-asserted ID, or anonymous worker access.
- A compromised worker credential must not grant submitter/operator access, database access, provider access, or the ability to choose a job generation/token. A compromised supervisor is an operator-managed host incident; Factory makes no host-containment guarantee.
- Do not claim that mTLS proves a unique physical machine, uncompromised supervisor, safe harness, or stopped process. It authenticates possession of configured key material. Cancellation, recovery, and process-stop evidence are addressed by #260. Factory makes no sandbox or security-isolation guarantee; operators own repository and harness threat risk.

## Required protocol tests before integration

These are future acceptance requirements, not evidence of implemented authentication:

1. Reject unknown, expired, disabled, revoked, wrong-CA, wrong-key, malformed, and incorrectly mapped credentials; verify generic responses and absence of secret/identity enumeration.
2. Verify duplicate credential mappings and duplicate principal IDs fail closed; verify atomic config reload/rotation with old/new overlap, revocation, rollback, and failed reload.
3. Attempt to spoof worker principal, worker ID, boot ID, role, job ID, generation, or attempt token in body/header/query; authenticated context must win and every unauthorized/stale mutation must be rejected.
4. Verify another principal cannot claim, read, heartbeat, mutate, finish, or acknowledge cancellation for an attempt; a submitter/operator credential cannot authenticate as a worker and worker credentials cannot use operator/submitter routes.
5. Revoke an active session while a worker is connected; its next claim/renewal/mutation fails, active work becomes suspect, history is retained, and no replacement begins without #260 stop proof.
6. Confirm boot IDs are generated by the trusted supervisor, change on restart, and cannot be reused to bypass active-session or generation fencing. Exercise a copied credential/competing boot and require safe conflict/operator resolution.
7. Verify the supervisor does not intentionally place worker private keys, mTLS sessions, DB/API credentials, session capabilities, or provider credentials in harness inputs, arguments, environment, descriptors, or mounts. Do not treat this as proof that hostile code cannot access authority available to the execution account.
8. Inject control-plane/database loss and ambiguous session/claim commits; assert no worker proceeds based on caller labels or assumed rollback and no duplicate claim/provider write starts.
9. Assert logs, errors, job projections, and attempt history never contain private key bytes, bearer/session credentials, or owner fencing tokens.

## Dependencies and rollout gate

- #258 is closed with a **test-only** PostgreSQL 18 single-primary contract. It does not provide a production coordinator, failover, authenticated workers, or runtime integration. Keep its primary-only/no-promotion/ambiguous-transaction restrictions.
- #259's design prerequisite is documented here; independent review and protocol-test implementation remain before it can be closed.
- #248 must incorporate this authenticated identity model into its approved ownership protocol and subsequently implement/test identity, generations, all fenced mutations, and conservative recovery. Until then no distributed worker rollout.
- #260 must specify session drain, credential revocation of active work, cancellation, and process-stop evidence; revocation never means the old process is dead.
- #261 must ensure the supervisor—not repository-controlled workload—owns credentials and that only a trusted serialized publisher can write to providers; uncertain provider writes block competition/retry.
- A host sandbox or isolation profile is not a prerequisite to this protocol and is not a Factory guarantee. A container, Kubernetes Pod, certificate, or worker lease alone does not change the operator-owned repository/harness threat risk. See the [Factory-unit MVP architecture](factory-unit-mvp.md) for the canonical target boundaries.
- #247 attribution is submitter identity, not worker identity. Any future progress API waits for #248's implemented authenticated ownership and exposes only bounded sanitized stages.

Session registration and heartbeat are implemented, but no authenticated job protocol, worker reassignment, or automatic recovery is implemented or authorized by this design. Select and test the production topology and all dependent protocols before rollout.
