# Local Compose API control plane

This is the **current development sample**, not the target Factory Worker MVP. The root `docker-compose.yml` starts PostgreSQL and a Controller using the static `factory-controller:local` image (also tagged `factory-web:local` for compatibility). By default it has **no Worker service**, so jobs can be admitted but remain queued. The legacy opt-in `worker` profile adds a separately configured `factory-worker:local` process that connects directly to PostgreSQL. The new explicit `remote-worker` profile instead runs the HTTP-polling Worker, which connects to the Controller over the private Compose network and has no database configuration.

The target requires Compose to run the Controller, PostgreSQL, and separate Worker clients as one user-facing product. Current Workers instead share PostgreSQL directly; see [Factory Worker MVP architecture](../roadmap/factory-unit-mvp.md) for the target boundary. This sample is for local development, not production or a security sandbox.

## Prerequisites and setup

Install Docker with Compose, Python 3, and OpenSSL 1.1.1 or newer. The smoke test uses OpenSSL's `req -addext` option to create a temporary test certificate; it checks the OpenSSL version before it builds or starts containers and prints a fixed error if the requirement is not met. The smoke test uses Python's standard-library `urllib` on the host (not curl). From the repository root:

```sh
python3 scripts/compose-local.py
make container-build
docker compose -f docker-compose.yml up -d --wait postgres provision-config api
docker compose -f docker-compose.yml exec -T api /factory probe --url http://127.0.0.1:8080/readyz
```

The generator creates `.local/factory-compose/` with mode `0700`; each generated configuration/credential file is mode `0600`. It prints no secret values and refuses to run if the credential directory already exists. Generated inputs include strict server JSON, strict legacy and HTTP remote Worker JSON, a private shared secret for the HTTP Worker API, a legacy operator API key, a named operator verifier and its client token, and the PostgreSQL password. Fresh configurations enable `remote_worker_api` using that generated secret. The generator does not modify existing setups; use `python3 scripts/compose-local.py --remote-worker-config-only` only when an existing setup already has the matching Controller setting and you intentionally want to add a matching Worker config and new secret. `.local/` is ignored by Git. Keep these files private. There is deliberately no implicit credential rotation: back up anything needed, stop the stack and remove the local generated setup and the `factory-config` and `factory-worker-config` volumes only when an explicit reset is intended, then rerun setup. Removing the `postgres-data` volume also destroys the database and is a separate destructive choice.

Older generated `.local/factory-compose/server.json` files may not contain the `web_ui` setting. The generator refuses to overwrite an existing setup, and the smoke test does not migrate or rewrite it: it checks for the dashboard configuration before adding a missing worker config, building images, or starting containers. To use the dashboard smoke test, edit the private `server.json` in place to include `"web_ui": {"enabled": true, "operator_id": "local-operator"}`; keep the directory at mode `0700` and the file at `0600`. The `local-operator` ID must match the named token already generated in this setup. The ordinary default Compose stack still works with a legacy config that has no dashboard option; no migration is required unless you need dashboard testing. If the config was already provisioned into the `factory-config` volume, back up the generated setup and volume data, stop Compose, then remove only that Compose project's `factory-config` volume so the edited config can be provisioned on restart. Keep the generated credentials and `postgres-data` volume; do not regenerate them or remove the database volume for this update. Then start the default stack with the command above.

The default one-shot provisioning service stages API configuration and credentials plus the PostgreSQL password. It does not read, require, or provision remote Worker inputs, so older generated setups remain compatible. Only the explicit `remote-worker` profile's one-shot provisioner reads and stages its strict config and secret. It does not require or provision `worker.json`, so previously generated directories without that file still start unchanged. The opt-in `provision-worker-config` service runs only with the legacy `worker` profile and requires a private `worker.json`; it stages that file in a unique private directory on the worker config volume. The separate `provision-remote-worker-config` service runs only with `remote-worker` and requires both `remote-worker.json` and its shared-secret file. Each is provisioned to separate private named volumes, read-only in the Worker, using the same no-overwrite, mode `0400`, UID `65532` rules. The remote Worker never mounts the PostgreSQL password volume or receives the PostgreSQL DSN/password. Its HTTP URL is `http://api:8080`; the generated strict Worker config explicitly sets `allow_insecure_http: true` for this private Compose network. That opt-in sends the Worker API shared secret without transport encryption, so do not copy it to other deployments or use HTTP beyond this trusted private network. Real deployments must use HTTPS. Both provisioners use owner-readable mode `0400` and runtime owners (`65532:65532` for API and worker config; `999:999` for the PostgreSQL password), then publish files with a no-overwrite hard link. Each final file appears atomically, but the files within each provisioner are not atomic as a set: an interrupted run can leave a valid subset provisioned. Retrying verifies every existing final against the generated source bytes, regular-file type, private mode, and expected owner, retains matching files unchanged, and fills missing files. A differing source or mismatched final is a conflict: provisioning stops without overwriting or deleting final data. Normal exit cleanup removes only this invocation's own uniquely created private staging directories; a forced kill can leave its private staging directory behind, which retries do not inspect or remove. There is no transaction manifest, commit marker, final-file rollback, or automatic conflict cleanup. If generated inputs or volume contents conflict, an operator must inspect and resolve the discrepancy deliberately, taking backups before any manual changes; do not treat automatic deletion as recovery. Concurrent runs with identical source inputs safely converge through no-overwrite hard links and per-file verification; different inputs conflict safely. API, legacy Worker, and remote Worker configs live in separate read-only config volumes. The legacy Worker config shares the API's PostgreSQL DSN and full limits, but omits caller API credentials. The HTTP remote Worker uses only its local repository and harness settings. The API starts only after the default provisioner exits successfully, mounts its config volume read-only, and runs as the image's non-root UID. The existing Compose controller image's strict config must name the separately provisioned remote Worker secret path for that optional API setting to be enabled. PostgreSQL receives its password from the private, read-only named secret volume, has durable named database storage, and no published host port. The API listens on `0.0.0.0:8080` inside its container but publishes only to host loopback (a randomly assigned loopback host port). The smoke test discovers that port rather than assuming a fixed local port. The readiness check invokes the static `/factory probe` command directly (no shell or curl in the API image); it makes a bounded, redirect-free GET request to `/readyz` and prints only a fixed success message.

The generated operator bearer token is in `.local/factory-compose/operator-token`; read it locally when configuring an API client. Do not paste it into shell history or logs. The generated server config enables the embedded dashboard for the `local-operator` named principal. The API key and verifier are different credential materials; the verifier contains only the named token's SHA-256 digest. Server JSON and the PostgreSQL password are also sensitive and must remain private. The PostgreSQL password is not interpolated into container environment variables. This sample uses a local PostgreSQL connection without TLS inside the Compose network; do not expose that network or API beyond a trusted local environment.

### Optional dashboard over operator-managed HTTPS

The dashboard uses a Secure session cookie. Keep that cookie security unchanged: access the dashboard through a trusted HTTPS endpoint, not the API's plain HTTP port. For this Compose setup, an operator may run a separately managed reverse proxy on host loopback with its TLS listener bound only to `127.0.0.1` (for example, `https://localhost:<proxy-port>`). Configure the proxy's upstream to the API's loopback-published HTTP endpoint shown by `docker compose -f docker-compose.yml port api 8080`; do not publish the API on a non-loopback interface. The proxy is external to the Compose stack and is not supplied or managed by Factory.

The application uses the incoming `Host` for its HTTPS same-origin check, and does not consume `Forwarded` or `X-Forwarded-*` headers for dashboard authentication. Preserve the browser's `Host`, `Origin`, and normal request path/method/body when proxying; do not rewrite them or rely on forwarded scheme headers. Allow only the dashboard paths in the [dashboard guide](rest-web-ui.md), including `/`, `/ui`, `/ui/`, `/ui/assets/*`, `/ui/login`, `/ui/logout`, `/ui/session`, and the explicitly documented `/ui/api/...` routes. Do not expose arbitrary API paths through the proxy. The dashboard itself also applies its narrow route allowlist, same-origin check, and CSRF checks to mutations.

The operator is responsible for the TLS certificate, hostname match, certificate renewal, browser trust, proxy access controls, and safe proxy configuration. Clients must trust the operator-selected certificate; do not disable certificate checks. See [the REST dashboard guide](rest-web-ui.md) for the exact application route allowlist and session behavior. The Compose smoke test uses only a temporary test certificate explicitly trusted by its test client; that is not an operator certificate or a production trust model.

## Optional local worker profile

The default profile does not resolve or mount a harness path. The worker's harness bind source is configured with `FACTORY_COMPOSE_HARNESS_DIR` (default `.local/factory-compose/harness`) and Compose `create_host_path: false`, so selecting `--profile worker` requires an operator-supplied existing harness directory without silently creating an empty host directory. The fixture in `scripts/fixtures/` is used only by the disposable smoke test; normal setup does not install it. The worker config points at `/opt/factory/harness` and uses the same fixed Pi-style argument vector as the API config. Fresh setup generates this private file. For a legacy setup without it, default Compose continues to work unchanged; only opt-in worker startup requires adding it with `python3 scripts/compose-local.py --worker-config-only` before selecting the worker profile.

The opt-in worker profile uses `worker-init` to initialize its private checkout and state volumes. The checkout is a clean committed Git working-tree root at `/var/lib/factory/checkouts/local`; the worker image's Git creates the initial disposable commit and sets ownership for UID/GID `65532`. The worker mounts its state volume at `/var/lib/factory/state`. `workers_enabled` remains `false` in server config, and worker/API limits match. This sample does not configure external PR publication, so it is only intended for local execution exercises.

## Optional HTTP remote Worker profile

The `remote-worker` profile is explicit and does not change default startup or the legacy direct-PostgreSQL `worker` profile. It starts the Worker with `factory worker remote --config /etc/factory/remote-worker.json`. The config uses `http://api:8080` with `allow_insecure_http: true`, a narrowly scoped opt-in for this private Compose network, local repository `/var/lib/factory/checkouts/local`, harness `/opt/factory/harness`, and the generated Worker API secret. The Worker runs as UID/GID `65532`, mounts its strict config and shared secret read-only, and uses separate checkout/state volumes. It has no PostgreSQL DSN or password mount. The Controller must use HTTPS in any real deployment; the server listener does not terminate TLS. Do not publish the API beyond host loopback.

To start the sample remote Worker after generating fresh Compose inputs and supplying the harness directory:

```sh
docker compose -f docker-compose.yml --profile remote-worker up -d --wait remote-worker
```

The smoke test uses this profile to prove an admitted job is claimed over HTTP, executed by the fixture harness, and recorded as `succeeded`.

## Verify admission and optional execution

Run the full disposable local smoke check:

```sh
make test-compose-local
```

It generates credentials only in a fresh setup and verifies modes and non-overwrite behavior. It also provisions a legacy source directory without `worker.json` through the default mode, confirms that no worker config is created, checks that worker-only provisioning fails closed while the file is absent, then uses the private worker-config helper and confirms worker provisioning succeeds. It gates and interrupts a provisioner after its first final file, then verifies retry completes provisioning without replacing that file; runs two concurrent provisioners with identical inputs and verifies they converge; and attempts provisioning with a different source API key, verifying the original remains unchanged. It also verifies mismatched operator data is preserved on conflict, rejects hard-linked source and final credentials, and confirms simultaneous provisioners with different inputs produce one immutable winner without replacing its files. A random project suffix isolates uniquely named smoke volumes and containers; the script refuses collisions before reset or cleanup and discovers the randomly published loopback API port. It then validates Compose configuration, builds the control-plane image, starts PostgreSQL and API, probes readiness, and submits one authenticated test job. Failure-path exercises use only volumes named for the unique disposable smoke-test project. It first confirms a no-execution job stays `queued` while the default stack runs without workers. It then validates both profile configurations, initializes disposable checkout/state volumes as UID `65532`, mounts a deterministic fixture harness, admits a legacy fixture job, and confirms it reaches `succeeded` with the expected result in its retained worktree. It stops that legacy Worker, starts the `remote-worker` profile, verifies the container has no PostgreSQL mount or environment setting and retains the existing nonroot/read-only boundaries, then admits a separate job and confirms HTTP claim, execution, `succeeded` outcome, and the expected retained artifact. Finally, a test-only HTTPS reverse proxy bound to host loopback uses a temporary certificate trusted only by the test client. It fetches the dashboard and assets, logs in with the generated named operator token, verifies the Secure cookie and CSRF session, admits a second job through the dashboard's same-origin route, starts the single Worker, checks the completed job and retained artifact, then logs out and confirms the old session is rejected. This proxy exists only during the test and is not part of the Compose product stack. The test uses a unique Compose project name and removes only those smoke-test containers and named volumes on exit; it will not tear down a separately running default Compose stack. Generated credentials remain and are not printed. Use `docker compose -f docker-compose.yml down` for a normal stop that preserves PostgreSQL and config volume data.

The smoke check uses Python's standard-library `urllib` on the host to submit and inspect an example request; it does not add curl, a client, or an execution utility to the API image. The API exposes the existing job-service semantics and its normal trust boundary; local containers do not make repository-controlled content safe to execute. Without the opt-in worker profile, admitted jobs remain queued across restarts with PostgreSQL persistence.
