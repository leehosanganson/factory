# REST job server

`factory server --config <absolute-path>` starts the authenticated local REST job service using a strict, server-only JSON file. The command requires exactly `--config` followed by an absolute path; it does not load the normal Factory CLI config. `factory server doctor --config <absolute-path>` checks strict config and local prerequisites without starting service resources; it is read-only and local-only, does not test provider reachability, open/create SQLite, start a listener, or run the workflow. `factory server --help` shows focused help without reading either config. Memory is the default; optional SQLite persistence and the configured GitHub PR provider are available when enabled. The service contract is in the [REST job contract](../roadmap/rest-api-contract.md); see the [OpenAPI specification](../openapi/rest-api-v1.json) for the published API definition. Compatible API changes update the spec and info.version; incompatible API changes publish a new versioned document.

The server validates each configured repository as an exact Git working-tree root before opening its listener, loads the protected shared operator key plus configured named-principal verifier files and provider token, initializes the selected bounded job store, and runs a fixed number of workers. The listener defaults to `127.0.0.1:8080`; explicitly choosing another interface exposes the API there and requires appropriate network controls. Authenticated clients can submit an allowlisted repository alias, task, and idempotency key, optionally with a numeric `issue` and bounded `issue_provenance` object (GitHub tracker/source/number/version/URL/sanitized title only). The legacy shared API key and named operator principals have operator-wide authority; named submitter principals can submit jobs, access only their own job detail/history/events, and list their own jobs. Submitters cannot call operations, cancel, or recovery routes. Job snapshots expose the stable `submitted_by` principal ID. Existing jobs are attributed to the migration identity `legacy-shared`; the former shared key cannot identify which individual submitted them. The ordinary task remains visible through authenticated job detail; issue body text is not duplicated in provenance. Provenance is caller-supplied and the server does not verify it against GitHub. The tuple `(tracker, source_repository, issue_number, version)` uniquely maps to one retained job across keys when the complete request matches; different request content conflicts with sanitized HTTP 409. Memory eviction removes that mapping with its job; SQLite keeps provenance for the retained record and refuses record eviction at capacity. See the [REST job client](rest-client.md) for explicit confirmed issue dispatch. Operators can list retained jobs through bounded read-only `GET /v1/jobs` pages with numeric `after`/`snapshot` continuation and inspect/cancel any job. Submitters use the same route but receive only their own jobs, with an opaque `cursor`/`next_cursor` pagination contract and no numeric sequence metadata. Submitter cursors are process-memory, principal-bound, expire after 15 minutes, and are invalidated on restart; operator numeric sequence pagination remains unchanged. Both listing shapes include only ID, status, and timestamps, omitting request/payload text and provider or event details. See [REST server operations](rest-server-operations.md) for exact continuation semantics. A queued job is canceled before claim and never executed; a running job receives cooperative context cancellation, remains `running` with `cancellation_requested: true` until its executor exits, then records its terminal event. Repeating while cancellation is pending returns the same accepted snapshot without another event; terminal or otherwise ineligible jobs conflict without mutation. `GET /v1/operations` provides count-only aggregate status behind the same bearer authentication; it does not expose job identities or payloads. Request bodies and task sizes are limited by config. The authenticated read-only `GET /v1/jobs/{id}/events` route provides an optional Server-Sent Events view of retained safe lifecycle events. It uses monotonically increasing per-job event IDs and `Last-Event-ID` for replay, polls bounded history every 250 ms (no per-client event queue), and never includes task text, event messages, provider data, logs, credentials, or paths. A stale cursor or already-truncated initial history for an active job returns `409 cursor_expired`; fetch status/history to establish a baseline. Terminal jobs close after exposing the available retained tail without claiming it is complete; if the terminal lifecycle event was evicted, a synthetic `terminal_snapshot` control frame reports only the terminal status. A stream sends a heartbeat every 15 seconds, ends after 25 seconds, enforces a two-second write deadline, and releases its slot on disconnect. At most 16 streams are admitted process-wide; excess streams receive `503 stream_capacity`. Terminal jobs close after their terminal event. Clients may reconnect using the last ID, or fall back to `GET /v1/jobs/{id}` and `/history`. Existing status/history and lifecycle routes are unchanged. The REST contract and error responses are documented in [the REST API contract](../roadmap/rest-api-contract.md); the [OpenAPI specification](../openapi/rest-api-v1.json) is version 1.4.0.

Each configured repository uses an isolated detached worktree per job and a separate state/output area. Results are rooted under `${XDG_STATE_HOME:-~/.local/state}/factory/rest-server`, with a server-specific, hashed repository-alias directory. Existing broad or unsafe directories are rejected; Factory does not change their permissions. Successful workspaces are eligible for cleanup after 24 hours only when protected completion metadata proves completion. A startup sweep and hourly sweeps remove eligible workspaces; failed, canceled, malformed, or ambiguous workspaces are retained. Processes under the server account are trusted operators with filesystem authority. Local-process execution is not a security sandbox.

The configured harness is a fixed executable and argument vector, never shell text. The server runs the requirements, implementation, review, and documentation workflow. Optional trusted operator-configured `verification_checks` run afterward as argv arrays without shell parsing; callers cannot provide or alter checks. With no checks configured (the default), no external verification checks run. The optional `parallel_subtasks` setting enables Factory's existing planner-driven parallel implementation within one job; omission and `enabled: false` preserve serial implementation. Parallelism is bounded per job (default 4, configured range 1–8), separately from `limits.workers`, which bounds concurrent jobs. Existing plan/scope/wave/integration/rollback safeguards are reused; if the workflow deems a checkout ineligible, implementation falls back to serial. This is not a sandbox: API-key holders and repository/harness content remain within the server account's local-process trust boundary. When GitHub is configured, the server commits verified changes on a job-specific branch, pushes only to the configured repository, and creates or updates the job's PR. A provider-configured job is successful only after its confirmed PR outcome has been recorded by the selected store. Authenticated job inspection includes the confirmed PR identity/URL and bounded verification evidence: configured checks are labeled `check-01`, `check-02`, etc. with passed/failed/canceled/not-completed outcomes, plus fixed limitations for checks not configured and the fact that agent-reported completion is not an independent correctness verdict. Check argv, output, transcripts, and host paths are not included in the API result. Provider credentials are loaded from a protected file and not passed to the harness. Factory never merges or deploys. Captured workflow output is bounded and not exposed through the HTTP API.

`/healthz` is a liveness endpoint; `/readyz` becomes ready only after runtime initialization, listener startup, and successful configured storage/provider probes. Per-job cancellation targets only the selected executor; it does not stop the service or other jobs. Shutdown is separate: it creates one 15-second default deadline before stopping cleanup, cancels the sweeper and waits only within that shared deadline, then closes HTTP serving and cancels/waits for workers using the remaining time. Workspace cleanup Git operations receive bounded contexts; uncertain cleanup retains workspaces. API keys and provider tokens are read once at startup; rotation requires a restart. Memory mode loses records on restart; SQLite preserves records and classifies interrupted jobs conservatively. Authenticated bodyless operator actions can mark eligible interrupted SQLite jobs failed/canceled only without persisted provider attempts/outcomes, or reconcile persisted provider identities through configured read-only provider lookup and atomically confirm success; neither action replays the workflow or writes to the provider. See the [operations guide](rest-server-operations.md). This is a single-process service, not a distributed queue or security boundary.

See [the REST server config reference](rest-server-config.md) for the strict JSON schema and [REST server operations](rest-server-operations.md) for health/readiness probes, aggregate operational status, backup/restore, restart recovery, and capacity guidance.
