# REST job server

`factory server --config <absolute-path>` starts the authenticated local REST job service using a strict, server-only JSON file. An optional embedded operator dashboard is configured by `web_ui.enabled` and `web_ui.operator_id`; it is disabled by default and serves only a constrained same-origin job API through a named-operator session. See the [dashboard and container guide](rest-web-ui.md). The command requires exactly `--config` followed by an absolute path; it does not load the normal Factory CLI config. `factory server doctor --config <absolute-path>` checks strict config and local prerequisites without starting service resources; it is read-only and local-only, does not test provider reachability, open/create SQLite, start a listener, or run the workflow. `factory server --help` shows focused help without reading either config. Memory is the default; optional SQLite or PostgreSQL persistence and the configured GitHub PR provider are available when enabled. PostgreSQL can be shared by a workers-disabled API control plane and separately launched `factory worker` processes; all-in-one local workers remain enabled by default. See [PostgreSQL Store](postgres-store.md), [REST worker process](rest-worker.md), and the [server configuration reference](rest-server-config.md) for backend and topology details. Factory does not provide a fleet coordinator. The service contract is in the [REST job contract](../roadmap/rest-api-contract.md); see the [OpenAPI specification](../openapi/rest-api-v1.json) for the published API definition. Compatible API changes update the spec and info.version; incompatible API changes publish a new versioned document.

The API server validates each configured repository as an exact Git working-tree root before opening its listener, loads the protected shared operator key plus configured named-principal verifier files, initializes the selected bounded job store, and runs a fixed number of local workers by default. Provider credentials are loaded by processes configured to execute jobs. PostgreSQL server configs may set `workers_enabled: false` to run only the API control plane while separate `factory worker` processes execute jobs. Worker mode and cross-process capacity rules are described in [REST worker process](rest-worker.md). The main API listener defaults to `127.0.0.1:8080`; explicitly choosing another interface exposes the API there and requires appropriate network controls. An optional `worker_listener` config starts a separate TLS listener, requires PostgreSQL or SQLite persistence, verifies client certificates against a configured CA, then maps the exact presented leaf certificate DER SHA-256 fingerprint to an operator-configured worker principal. Its bounded routes are `GET /healthz`, `GET /readyz`, `POST /v1/worker/session`, and `DELETE /v1/worker/session/{session_id}`; it is not mounted on the job API. Registration stores only principal, worker-supplied boot ID, server-issued session ID, state, and timestamps; the same active principal/boot retry returns its session, a different active boot conflicts, and a retired principal/boot pair remains permanently unusable. Only explicit authenticated retirement permits a different boot ID to register; retirement does not enable implicit takeover. Session records and append-only registration/retirement audit events are SQL-persisted. This is identity/session lifecycle only: it does not expose job claims, ownership, execution, reassignment, or replay, and the boot ID is an incarnation label rather than proof of authentication. Certificate mapping configuration is startup-loaded; this slice does not implement dynamic rotation/revocation. An optional GitHub `issues.labeled` webhook is served at `POST /v1/webhooks/github/issues`; it admits configured issues into the existing Thread/Job lifecycle using raw-byte HMAC verification, exact source/label checks, and server-configured repository-alias and owner-principal mappings. Delivery ID and body digest commit atomically with the Thread and Job under durable SQLite/PostgreSQL storage; neither raw event body nor secret is retained. It is independent of the issue poller, so overlapping source/label config can admit duplicate work. See [GitHub issue webhook](github-issue-webhook.md). Authenticated clients can submit standalone Jobs through `POST /v1/jobs` as before, and can create one direct-request Thread plus its initial Job atomically through `POST /v1/threads`; `GET /v1/threads/{id}` returns its stable member Jobs and derived status; `POST /v1/threads/{id}/jobs` atomically appends a direct-request Job with a Thread-scoped idempotency key. `POST /v1/threads/{id}/complete` is a bodyless authenticated owner action that explicitly closes a Thread at any aggregate status; repeated calls are idempotent and expose `completed_at`/`completed_by` through Thread inspection. Aggregate status remains a projection over Jobs, and Done does not imply closure or mutate Job state. Completion and admission serialize across durable Store connections; an append that wins commits before close, while new appends after close receive `409 thread_closed` (an exact retry of a previously admitted member remains idempotent). Thread creation and member admission accept only repository/task and share the existing Job capacity. Operators inspect any Thread but can append/complete only their own; submitters inspect, append, and complete only their own (with missing/foreign Threads both returning 404). Scheduled and standalone Jobs remain outside Threads. Each transition of an unclosed Thread aggregate to Done commits one logical owner-inbox notification atomically with the terminal Job update. The authenticated `GET /v1/notifications` inbox filters to the Thread submitter principal, exposes only notification ID, Thread ID, fixed `done` status, and timestamp, and supports bounded newest-first pagination. It does not send email, push, or chat messages and has no read acknowledgement. Reads never create notifications; adding a member to an open Done Thread reopens the aggregate, and a later Done transition emits a new notification. Memory inbox records are volatile; SQLite and PostgreSQL persist notifications across restart with bounded retention. Notification creation failures roll back the corresponding terminal status transition for normal retry. REST dashboard exposure remains intentionally limited to its explicit job-only route allowlist. Separately, authenticated clients can submit an allowlisted repository alias, task, and idempotency key through `/v1/jobs`, optionally with a numeric `issue` and bounded `issue_provenance` object (GitHub tracker/source/number/version/URL/sanitized title only). The legacy shared API key and named operator principals have operator-wide authority; named submitter principals can submit jobs, access only their own job detail/history/events/provenance, and list their own jobs. Submitters cannot call operations, cancel, or recovery routes. Job snapshots expose the stable `submitted_by` principal ID. Existing jobs are attributed to the migration identity `legacy-shared`; the former shared key cannot identify which individual submitted them. The ordinary task remains visible through authenticated job detail; issue body text is not duplicated in provenance. `GET /v1/jobs/{id}/issue-provenance` and `factory rest issue-provenance` expose only the bounded provenance projection (not task text) for an eligible job. Provenance is caller-supplied and the server does not verify it against GitHub. The tuple `(tracker, source_repository, issue_number, version)` uniquely maps to one retained job across keys when the complete request matches; different request content conflicts with sanitized HTTP 409. Memory eviction removes that mapping with its job; SQLite and PostgreSQL keep provenance for retained records and refuse record eviction at capacity. See the [REST job client](rest-client.md) for explicit confirmed issue dispatch. Operators can list retained jobs through bounded read-only `GET /v1/jobs` pages with numeric `after`/`snapshot` continuation and inspect/cancel any job. Submitters use the same route but receive only their own jobs, with an opaque `cursor`/`next_cursor` pagination contract and no numeric sequence metadata. Submitter cursors are process-memory, principal-bound, expire after 15 minutes, and are invalidated on restart; operator numeric sequence pagination remains unchanged. Both listing shapes include only ID, status, and timestamps, omitting request/payload text and provider or event details. See [REST server operations](rest-server-operations.md) for exact continuation semantics. A queued job is canceled before claim and never executed; a running job receives cooperative context cancellation, remains `running` with `cancellation_requested: true` until its executor exits, then records its terminal event. Repeating while cancellation is pending returns the same accepted snapshot without another event; terminal or otherwise ineligible jobs conflict without mutation. `GET /v1/operations` provides count-only aggregate status behind the same bearer authentication; it does not expose job identities or payloads. Request bodies and task sizes are limited by config. The authenticated read-only `GET /v1/jobs/{id}/events` route provides an optional Server-Sent Events view of retained safe lifecycle events. It uses monotonically increasing per-job event IDs and `Last-Event-ID` for replay, polls bounded history every 250 ms (no per-client event queue), and never includes task text, event messages, provider data, logs, credentials, or paths. A stale cursor or already-truncated initial history for an active job returns `409 cursor_expired`; fetch status/history to establish a baseline. Terminal jobs close after exposing the available retained tail without claiming it is complete; if the terminal lifecycle event was evicted, a synthetic `terminal_snapshot` control frame reports only the terminal status. A stream sends a heartbeat every 15 seconds, ends after 25 seconds, enforces a two-second write deadline, and releases its slot on disconnect. At most 16 streams are admitted process-wide; excess streams receive `503 stream_capacity`. Terminal jobs close after their terminal event. Clients may reconnect using the last ID, or fall back to `GET /v1/jobs/{id}` and `/history`. Existing status/history and lifecycle routes are unchanged. The REST contract and error responses are documented in [the REST API contract](../roadmap/rest-api-contract.md); the [OpenAPI specification](../openapi/rest-api-v1.json) is version 1.10.0.

Each configured repository uses an isolated detached worktree per job and a separate state/output area. Results are rooted under `${XDG_STATE_HOME:-~/.local/state}/factory/rest-server`, with a server-specific, hashed repository-alias directory. Existing broad or unsafe directories are rejected; Factory does not change their permissions. Successful workspaces are eligible for cleanup after 24 hours only when protected completion metadata proves completion. A startup sweep and hourly sweeps remove eligible workspaces; failed, canceled, malformed, or ambiguous workspaces are retained. Processes under the server account are trusted operators with filesystem authority. Local-process execution is not a security sandbox.

The configured harness is a fixed executable and argument vector, never shell text. The server runs the requirements, implementation, review, and documentation workflow. Optional trusted operator-configured `verification_checks` run afterward as argv arrays without shell parsing; callers cannot provide or alter checks. With no checks configured (the default), no external verification checks run. The optional `parallel_subtasks` setting enables Factory's existing planner-driven parallel implementation within one job; omission and `enabled: false` preserve serial implementation. Parallelism is bounded per job (default 4, configured range 1–8), separately from `limits.workers`, which bounds concurrent jobs. Existing plan/scope/wave/integration/rollback safeguards are reused; if the workflow deems a checkout ineligible, implementation falls back to serial. This is not a sandbox: API-key holders and repository/harness content remain within the server account's local-process trust boundary. When GitHub is configured, the server commits verified changes on a job-specific branch, pushes only to the configured repository, and creates or updates the job's PR. A provider-configured job is successful only after its confirmed PR outcome has been recorded by the selected store. Authenticated job inspection includes the confirmed PR identity/URL and bounded verification evidence: configured checks are labeled `check-01`, `check-02`, etc. with passed/failed/canceled/not-completed outcomes, plus fixed limitations for checks not configured and the fact that agent-reported completion is not an independent correctness verdict. Check argv, output, transcripts, and host paths are not included in the API result. Provider credentials are loaded from a protected file and not passed to the harness. Factory never merges or deploys. Captured workflow output is bounded and not exposed through the HTTP API.

`/healthz` is a liveness endpoint; `/readyz` becomes ready only after runtime initialization, listener startup, and successful configured storage/provider probes. Per-job cancellation targets only the selected executor; it does not stop the service or other jobs. Shutdown is separate: it creates one 15-second default deadline before stopping cleanup, cancels the sweeper and waits only within that shared deadline, then closes HTTP serving and cancels/waits for workers using the remaining time. Workspace cleanup Git operations receive bounded contexts; uncertain cleanup retains workspaces. API keys and provider tokens are read once at startup; rotation requires a restart. Memory mode loses records on restart; SQLite and PostgreSQL preserve records and classify interrupted jobs conservatively. Authenticated bodyless operator actions can mark eligible interrupted durable-store jobs failed/canceled only without persisted provider attempts/outcomes, or reconcile persisted provider identities through configured read-only provider lookup and atomically confirm success when the executor is available; neither action replays the workflow or writes to the provider. With a workers-disabled API control plane and separate workers, reconciliation is unavailable through the API because worker processes do not expose the required callback. PostgreSQL CLI backup and portable recovery bundles are not supported; those commands remain SQLite-only. See the [operations guide](rest-server-operations.md). Memory and SQLite deployments are single-process stores; PostgreSQL supports shared API/worker processes with a database-wide execution cap, but no fleet coordinator or security boundary.

See [the REST server config reference](rest-server-config.md) for the strict JSON schema and [REST server operations](rest-server-operations.md) for health/readiness probes, aggregate operational status, SQLite backup/restore, restart recovery, and capacity guidance.
