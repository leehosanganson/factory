# REST job server

`factory server --config <absolute-path>` starts the authenticated local REST job service using a strict, server-only JSON file. The command requires exactly `--config` followed by an absolute path; it does not load the normal Factory CLI config. `factory server --help` shows focused help without reading either config. Memory is the default; optional SQLite persistence and the configured GitHub PR provider are available when enabled. The service contract is in the [REST job contract](../roadmap/rest-api-contract.md).

The server validates each configured repository as an exact Git working-tree root before opening its listener, loads the protected shared API key and configured provider token, initializes the selected bounded job store, and runs a fixed number of workers. The listener defaults to `127.0.0.1:8080`; explicitly choosing another interface exposes the API there and requires appropriate network controls. Authenticated clients can submit an allowlisted repository alias, task, and idempotency key, then inspect job status and bounded history. Request bodies and task sizes are limited by config. The REST contract and error responses are documented in [the REST API contract](../roadmap/rest-api-contract.md).

Each configured repository uses an isolated detached worktree per job and a separate state/output area. Results are rooted under `${XDG_STATE_HOME:-~/.local/state}/factory/rest-server`, with a server-specific, hashed repository-alias directory. Existing broad or unsafe directories are rejected; Factory does not change their permissions. Successful workspaces are eligible for cleanup after 24 hours only when protected completion metadata proves completion. A startup sweep and hourly sweeps remove eligible workspaces; failed, canceled, malformed, or ambiguous workspaces are retained. Processes under the server account are trusted operators with filesystem authority. Local-process execution is not a security sandbox.

The configured harness is a fixed executable and argument vector, never shell text. The server runs the requirements, implementation, review, and documentation workflow. Optional trusted operator-configured `verification_checks` run afterward as argv arrays without shell parsing; callers cannot provide or alter checks. With no checks configured (the default), no external verification checks run. When GitHub is configured, the server commits verified changes on a job-specific branch, pushes only to the configured repository, and creates or updates the job's PR. A provider-configured job is successful only after its confirmed PR outcome has been recorded by the selected store. Provider credentials are loaded from a protected file and not passed to the harness. Factory never merges or deploys. Captured workflow output is bounded and not exposed through the HTTP API.

`/healthz` is a liveness endpoint; `/readyz` becomes ready only after runtime initialization, listener startup, and successful configured storage/provider probes. Shutdown creates one 15-second default deadline before stopping cleanup, cancels the sweeper and waits only within that shared deadline, then closes HTTP serving and cancels/waits for workers using the remaining time. Workspace cleanup Git operations receive bounded contexts; uncertain cleanup retains workspaces. API keys and provider tokens are read once at startup; rotation requires a restart. Memory mode loses records on restart; SQLite preserves records and classifies interrupted jobs conservatively. This is a single-process service, not a distributed queue or security boundary.

See [the REST server config reference](rest-server-config.md) for the strict JSON schema and [REST server operations](rest-server-operations.md) for health/readiness probes, backup/restore, restart recovery, and capacity guidance.
