# Issue work intake and tracking

`factory work` provides a local CLI for durable issue-work request intake, inspection, and explicitly recording human direction for a paused request. Submission does not fetch an issue, create a pull request, or start engineering. The `issue` command fetches and displays one ephemeral read-only snapshot for an existing queued request. The explicit `refresh` command fetches once and persists an immutable observation when its snapshot version is new; `history` lists those durable observations and the reconciled lifecycle state. The opt-in `watch` command polls in the foreground until the issue closes; this is manual foreground polling, not an autonomous worker or PR engineering. `respond` records an instruction only for an issue whose persisted reconciled lifecycle is `waiting_for_human`, whose latest observation is open, and whose exact version was supplied. It does not change lifecycle or queue state, resume engineering, invoke an agent, or contact GitHub. `directions` displays only locally persisted records.

The internal `IssueTracker` contract has a read-only GitHub implementation, `GitHubIssueTracker`. Its `GetIssue` method returns a provider-neutral snapshot containing repository, issue number, title, body, state, URL, update time, and a version fingerprint over the exposed snapshot fields. GitHub reads use `gh api` and the GitHub CLI's existing authentication; Factory does not store credentials. Repository references must be `owner/repo` and issue references positive numbers. GitHub pull requests are detected and rejected as non-issues. `work issue` first loads the queued item and rejects missing requests or non-GitHub trackers before making a provider call. It fetches once and prints the queued identity alongside snapshot title, state, update time, version, and URL. Inspection does not mutate or persist the queue item, poll, claim work, start a worker, or write to GitHub.

A separate provider-neutral `CodeRepository` contract has a read-only GitHub implementation, `GitHubCodeRepository`. Its `GetPullRequest(repository, number)` method returns a provider-neutral snapshot with repository, number, title, body, open/closed state, URL, head/base branches and commit IDs, update time, and a fingerprint over the exposed fields. It validates the response repository, number, and pull-request URL. The adapter invokes only `gh api --method GET` and relies on existing `gh` authentication; Factory does not store credentials. It is an internal adapter only: no CLI command, polling, worker, branch creation, PR creation, or PR update is implemented.

```sh
factory work submit --tracker <provider> --issue <issue-ref> --code-host <provider> --repository <repo> [--dedup-key <key>]
factory work list
factory work get <dedup-key>
factory work issue <dedup-key>
factory work refresh <dedup-key>
factory work history <dedup-key>
factory work watch <dedup-key> [--interval <duration>]
factory work respond <dedup-key> --version <issue-version> --instruction <text>
factory work directions <dedup-key>
```

Tracker and code-host provider names must match the provider-name validation used by `WorkRequest` (`[a-z][a-z0-9-]*`). Issue references and repository identifiers are provider-specific strings. Unless `--dedup-key` is supplied, Factory derives a filesystem-safe key from a SHA-256 digest of tracker, issue reference, code host, and repository. Repeating the same identity is idempotent. Reusing a key for different identity fields reports a conflict; an explicit different key permits intentional separate work.

Requests are stored in the private local queue at `<state_dir>/factory/work-requests`, or `${XDG_STATE_HOME:-~/.local/state}/factory/work-requests` when `state_dir` is unset. Issue observations, lifecycle state, and human-direction records are stored separately under `<state_dir>/factory/work-observations`; snapshot and direction records use hashed filenames, and snapshot/lifecycle/direction writes use restrictive permissions and atomic writes under a shared single-host file lock. Direction payloads are capped at 16 KiB; exact repeats for a request/version are idempotent, while a different instruction for that same version is rejected rather than overwritten. A later eligible issue version may have a separate direction record. A request key and snapshot `Version` identify one immutable observation: repeating the same snapshot version is idempotent, while a different version is retained as a separate history entry. `history` displays title, state, update time, version, and URL in update-time order, followed by lifecycle status. Lifecycle reconciliation uses persisted `ObservedAt` order (version is the deterministic tie-break for tied timestamps), not provider `UpdatedAt` order. New versions are timestamped under the store lock with `ObservedAt` strictly later than every prior observation for the same request, including rapid writes; duplicate versions keep their original timestamp. Legacy records with tied timestamps still rely on the version tie-break and may not reflect their original record order. No credentials are stored in observation records or lifecycle state.

`list` and `get` display persisted request identity and state; they do not claim requests or start work. `respond` pins a sanitized, locally stored instruction to the supplied current issue version; a stale version, closed issue, missing observation, or lifecycle other than exactly `waiting_for_human` is rejected without writes. `directions` lists saved instructions in recorded-time order, without a provider call. Recording or inspecting direction is only durable human input: there is no approval action, lifecycle transition, worker/resume, agent invocation, branch/PR action, or GitHub write. `issue` performs a single GitHub read and displays the snapshot without persisting it. `refresh` performs one GitHub read, persists its snapshot, reports whether it was newly recorded or already present, and reconciles/displays lifecycle status. `watch` loads the queued request once, rejects missing requests and non-GitHub trackers before network access, fetches immediately, then polls at one-minute intervals by default (or a positive Go duration supplied with `--interval`). Each fetched snapshot is persisted and shown with its new/duplicate status and explicit lifecycle status. The first open observation establishes `baseline`; a subsequent distinct open version transitions to `waiting_for_human`. Watching continues to poll and record distinct versions while in that state. The first observed closed snapshot transitions to terminal `stopped`, including closure before any open snapshot; closed state remains terminal if a later open snapshot is recorded. Closure preserves every snapshot and any unrelated worktree/PR artifacts; it only stops this observer. `history` reconciles and displays the current lifecycle state without a provider call. Reconciliation can rebuild a missing/stale lifecycle record from observation history after a crash between observation and state writes; version-keyed observations remain idempotent. Observation chronology uses local `ObservedAt`, with version tie-breaks when timestamps match. New versions receive strictly increasing `ObservedAt` timestamps under the store lock, so rapid writes preserve record order; duplicate versions remain unchanged. Legacy records with tied timestamps lack recoverable insertion order, so their deterministic version tie-break can differ from their original record order or provider update order. Watching exits successfully when lifecycle is stopped and stops on context cancellation or provider/store error. Watch does not claim or mutate queue state. These are explicit commands: there is no autonomous worker, PR engineering, or issue/PR write. The internal code-host PR adapter is read-only and is not connected to the CLI. The local queue is single-host and is not a distributed broker.
