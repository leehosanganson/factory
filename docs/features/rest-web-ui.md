# Embedded REST operator dashboard

The REST server can optionally serve an embedded browser dashboard from `/` on the existing API listener. It is disabled unless strict server JSON includes `web_ui.enabled: true` and `web_ui.operator_id` naming an enabled named operator. The browser login accepts that operator's configured token or an enabled named submitter's configured token; the shared legacy key and other named operators cannot log in through the UI.

The browser supports two separate views. The operator dashboard remains focused on bounded operator job listing and inspection, safe worker/workflow stage summaries, retained lifecycle history and event streaming, standalone Job admission, cooperative cancellation, direct Thread browsing, creation, inspection, member append, and explicit completion, plus read-only Worker session inspection. Enabled named submitters can also sign in with their own configured token and use a separate user workbench: draft tickets and queue them as Threads with their first Job, send follow-ups, inspect owned Threads and Job outcomes, and review owner-only completion notices in the Inbox. The submitter view does not show operator jobs, schedules, or Worker sessions. It refreshes the board, selected Thread, and Inbox while signed in; reloading restores the Thread list and persisted safe outcome/notices from the server. The submitter proxy allows only the bounded Thread list/create/detail/append, owned Job detail, and owner-only Inbox reads; it does not expose Job history, whose operator projection includes worker and progress metadata. Submitter Thread listing is limited to the newest 50 entries in this slice; older-page pagination is deferred. It does not store the browser's raw token in its session. The shared legacy API key does not authenticate a browser session. The operator dashboard loads Thread summaries newest-first by immutable initial Job admission order (50 per page), and operators can load older pages. Selecting a Thread fetches its existing detail view with ordered member Job IDs/status/timestamps. The summary projection includes only Thread ID/status/timestamps/completion time; it omits task/request, owner ID, member IDs, provider, Worker, and progress data. Append and completion controls remain visible for a selected open Thread; the API enforces ownership, so inspecting another owner's Thread does not grant mutation rights and the UI shows the safe API error. Submitter Thread and Job details use similarly safe projections: they show status/timestamps and, after terminal status, bounded verification check outcomes, fixed limitations, and the owner-only text reply for a successful Pi Thread Job (up to 8 KiB), not request text, provider data, worker identity, or raw output. Append uses an idempotency key that stays stable for retries of the same payload; a changed payload starts a new intent. The controls block duplicate concurrent submissions and refresh Thread detail after a mutation. A `thread_closed` response refreshes the current Thread and reports that it is closed. Thread detail projections are built server-side from allowlisted fields and exclude task/request and provider data. The dashboard can create persistent schedules and show up to 20 recent schedules with status, UTC cron, persisted pending/skipped summaries, and up to five recent run outcomes per schedule. Schedule creation accepts a five-field UTC cron expression, repository alias, and task; cron recurrence is at least one minute. Create retries with the same unchanged form use the same idempotency key; changed form content starts a new request key, and only one create request can be active at a time. The create response uses the existing redacted schedule projection and does not return task, repository, or owner. The task stays in the form after errors and is cleared after success. Run links open the existing Job inspection. Schedule list and run projections omit task text, owner, and repository fields. Each row offers edit, pause/resume, and remove controls. The dashboard fetches the full definition only after Edit is opened, and displays its task and repository only inside that form. Every mutation uses the latest known schedule revision in `If-Match`; stale or missing revision responses refresh the list and ask the operator to review and act again rather than retrying the mutation automatically. Remove confirms before marking the schedule removed; admitted Jobs are unchanged. The dashboard's source is React with TypeScript; its production Vite assets are committed and embedded by the Go server. Rebuild with `make frontend-build` and check generated assets with `make frontend-check` (Node.js 24 and npm 11 required for frontend builds). Run the authenticated operator and submitter browser journeys with `make test-dashboard-e2e`; it requires Go, Node.js/npm, Python 3, OpenSSL, and Playwright's Chromium browser. Selecting a job scrolls its details into view, using automatic scrolling when `prefers-reduced-motion: reduce` is requested and smooth scrolling otherwise. The Worker sessions panel shows only principal ID, server session ID, stored status, creation time, retirement time, and raw heartbeat timestamp. A heartbeat is advisory only; the panel does not infer online/offline state, availability, assignment, or progress. The control is read-only. It displays bounded sessions newest-first and sends both `before_created_at` and `before_id` together when loading older pages. The same-origin operator proxy exposes only `GET /v1/operations`, `GET /v1/worker-sessions` (with `limit`, or the paired `before_created_at` and `before_id` cursors), `GET /v1/jobs`, `POST /v1/jobs`, `GET /v1/jobs/{id}`, `GET /v1/jobs/{id}/history`, `GET /v1/jobs/{id}/events`, `POST /v1/jobs/{id}/cancel`, `GET/POST /v1/threads`, `GET /v1/threads/{id}`, `POST /v1/threads/{id}/jobs`, `POST /v1/threads/{id}/complete`, `GET/POST /v1/schedules`, `GET/PATCH/DELETE /v1/schedules/{id}`, and `GET /v1/schedules/{id}/runs` (limited to five runs). Its separate submitter proxy allows only `GET /v1/threads` (bounded to the first 50 newest Threads in this slice), `POST /v1/threads`, `GET /v1/threads/{id}`, `POST /v1/threads/{id}/jobs`, `GET /v1/jobs/{id}`, and `GET /v1/notifications` (with bounded `limit` and `before` query fields). Older submitter Thread pages are deferred; Job history is not available through the submitter proxy. Submitter reads use the authenticated principal's ownership filter. Mutating requests in either view require a same-origin check and CSRF token. Schedule creation and mutations still require SQLite or PostgreSQL persistence; memory mode returns `503 durable_store_required`. The dashboard cannot invoke schedule audit history, recovery, provenance, Worker registration or retirement, or arbitrary REST routes. Worker session listing is available only to the enabled named operator configured for the dashboard. The dashboard session does not make it a general-purpose operator API. Mutating requests require a same-origin check and CSRF token.

## Submitter ticket board

- Enter a repository alias and task, then select **Add draft**. The draft exists only in this tab's memory. Adding it does not create a Thread or admit a Job. Drafts do not survive reload, sign-out, or a change to the signed-in session.
- Drag a draft into the dashed **Work** drop zone or use **Queue** on the card (including on mobile or with a keyboard). Both use the existing Thread create operation, which admits its first Job. If the attempt fails or the reply is lost, retry **Queue** on the same draft to reuse its request key. **Discard** only removes the local draft; it does not cancel a Job that may already have been admitted.
- Only drafts can be dragged. The server's recorded Thread status places submitted tickets in **Work** (queued or running Jobs), **Needs Attention** (`need_attention`), or **Finished** (all Jobs reached an outcome). Finished is not an approval or a success verdict. An unrecognized status appears in **Unclassified**.
- Open a submitted ticket to inspect its Jobs or send a follow-up where available. The Inbox still shows recorded completion notices. After reload, submitted cards come from the server's Thread summaries; the board does not retain or show the original draft text on them.

The operator dashboard shows the `recovery_needed` count from the existing [aggregate operations endpoint](rest-server-operations.md#aggregate-operational-status). The count loads on sign-in and updates when the operator selects **Refresh**. A reported zero is distinct from **Unavailable**. The count does not show whether a Worker has stopped and does not trigger any recovery action.

In either browser view, selecting a Thread moves keyboard focus to its detail heading and scrolls it into view. Background refreshes update the details without moving focus or scrolling.

## Broader target user workbench (partially implemented)

The Factory Worker MVP requires a browser UI for users to create and follow Threads, submit and append Job requests, read results and outcomes, and receive in-product notifications. Operators also manage recurring schedules and inspect their admitted runs. This is broader than the current dashboard described above.

The target Controller assigns Jobs to separate Workers. Each Worker selects one harness from its own operator-configured set; the user and request do not select a harness. Worker mTLS, per-worker identity, registration/session management, and issue poller/webhook intake are deferred from this MVP. The [Factory Worker MVP architecture](../roadmap/factory-unit-mvp.md) defines this target and distinguishes it from the shipped dashboard, Worker process, and schedule APIs. The target does not include remote host or harness provisioning.

Sessions are held in process memory, capped at 1,000 live sessions, and expire after eight hours. The browser receives an HttpOnly, Secure, SameSite=Strict session cookie; the CSRF token exists only in page memory. HTTPS is required for the cookie, so deployments should use a trusted TLS endpoint/proxy and an appropriately controlled network. The UI uses a restrictive content security policy and renders API values as text. It does not display task content, raw event messages, transcripts, check output, or host-path metadata. Harness reply text is not a secret redactor. The browser views are convenience interfaces, not separate security boundaries; the API remains available under its existing authentication contract.

## Control-plane container

The root `Dockerfile` builds `factory-controller:local` (also tagged `factory-web:local`) and `factory-worker:local` from one shared build-stage executable. The Controller target remains static and non-root, includes the embedded dashboard assets, and defaults to `/factory server --config /etc/factory/server.json`. It requires PostgreSQL persistence with local workers disabled and contains no Git or harness. The Worker target is non-root, includes Git, and defaults to `/factory worker --config /etc/factory/worker.json`. Both role checks are operational guardrails only, not security boundaries. Running the executable without an image role retains normal CLI behavior and the all-in-one server's default local worker setting. The Controller serves the API on the usual listener (port 8080); neither image is a sandbox or fleet manager.

Build both images locally with `make container-build` when Docker is available.
