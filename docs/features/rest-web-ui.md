# Embedded REST operator dashboard

The REST server can optionally serve an embedded browser dashboard from `/` on the existing API listener. It is disabled unless strict server JSON includes `web_ui.enabled: true` and `web_ui.operator_id` naming an enabled named operator. The browser login accepts only that operator's configured token; the shared legacy key and other named operators cannot log in through the UI.

Today this is a **job-only operator dashboard**, not the target workbench. It supports bounded operator job listing and inspection, safe worker/workflow stage summaries, retained lifecycle history and event streaming, job admission, and cooperative cancellation. Selecting a job scrolls its details into view, using automatic scrolling when `prefers-reduced-motion: reduce` is requested and smooth scrolling otherwise. The same-origin proxy exposes only `GET /v1/jobs`, `POST /v1/jobs`, `GET /v1/jobs/{id}`, `GET /v1/jobs/{id}/history`, `GET /v1/jobs/{id}/events`, and `POST /v1/jobs/{id}/cancel`. It cannot invoke operations, recovery, provenance, schedules, Threads, Worker registration, or arbitrary REST routes. Mutating requests require a same-origin check and CSRF token.

## Target workbench (not implemented)

The target UI serves operators and developers and supports ongoing development work: inspect and manage Threads/Jobs, Auto or named-Worker routing, recurring schedules, and configured multi-source webhook integrations as the required APIs become available. It may register or configure Worker identities. It does not remotely provision compute, install Factory, install harnesses, or choose a harness per request; each Worker uses its operator-configured default harness/profile. Separately launched `factory worker` processes and shared-PostgreSQL operation are not registered fleet Workers.

Current schedule API routes and dispatch are implemented separately. Submitters can manage their own schedules, and operators can manage schedules across owners while preserving creator attribution; only submitters can create schedules. The API uses strict five-field UTC cron and has no schedule UI. The target operator workbench remains unimplemented; it should use the existing API rather than duplicate schedule ownership or invent recurrence behavior. The current webhook implementation is only GitHub `issues.labeled`; the target multiple-source authenticated webhook contract is not shipped.

Sessions are held in process memory, capped at 1,000 live sessions, and expire after eight hours. The browser receives an HttpOnly, Secure, SameSite=Strict session cookie; the CSRF token exists only in page memory. HTTPS is required for the cookie, so deployments should use a trusted TLS endpoint/proxy and an appropriately controlled network. The UI uses a restrictive content security policy and renders API values as text. It does not display task content, raw event messages, transcripts, check output, or host paths. The dashboard is an operator convenience, not a separate security boundary; the API remains available under its existing authentication contract.

## Control-plane container

The root `Dockerfile` builds `factory-controller:local` (also tagged `factory-web:local`) and `factory-worker:local` from one shared build-stage executable. The Controller target remains static and non-root, includes the embedded dashboard assets, and defaults to `/factory server --config /etc/factory/server.json`. It requires PostgreSQL persistence with local workers disabled and contains no Git or harness. The Worker target is non-root, includes Git, and defaults to `/factory worker --config /etc/factory/worker.json`. Both role checks are operational guardrails only, not security boundaries. Running the executable without an image role retains normal CLI behavior and the all-in-one server's default local worker setting. The Controller serves the API on the usual listener (port 8080); neither image is a sandbox or fleet manager.

Build both images locally with `make container-build` when Docker is available.
